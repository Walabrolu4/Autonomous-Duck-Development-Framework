<a id="wiki-foundations--overview"></a>
## What Is ADDF Light Games?


ADDF Light Games is a **human-guided, file-first AI game-development methodology**. It helps someone go from “I want to make a game” to a testable playable slice without requiring a complete game design document, a specific game engine, or an autonomous agent platform.

The short loop is **Research → Design / Ideation → Implement → Refine → Acceptance**. It repeats for each bounded sprint. Research reveals uncertainty; Design chooses a viable experience; Implement produces approved changes; Refine responds to evidence; Acceptance belongs to the person playing or evaluating the result.

<a id="wiki-foundations--overview--when-to-use"></a>
### When to use

Use Light for solo developers, game-design students, prototypes, interaction designers, small teams, and developers learning from AI assistance. The first supported domain is **games and interactive playable experiences**, not a general replacement for original ADDF's broader software-development governance.

The methodology works through a plain chat assistant and Markdown. A coding agent is optional for early discovery but valuable after you approve a technical plan. Claude Code, Codex and OpenClaw are optional adapters, **not requirements**.

<a id="wiki-foundations--overview--what-light-means"></a>
### What “Light” means

Light describes the **user's operational workload**, not less rigorous permissions or shallow explanations. The documentation may be exhaustive while the runtime starts with **six files** and only adds the three-file sprint pack when a milestone exists.

The agent researches, teaches relevant tradeoffs, drafts documentation, proposes actions and records actual results. The person decides consequential design direction, authorizes precise implementation scope and judges the playable outcome.

You should spend your attention on **what the player does and what you learn from testing**, not on manually writing a dozen administrative files.

<a id="wiki-foundations--overview--the-two-repositories"></a>
### The two repositories

The **framework distribution** lives in the `ADDF_light_games` Git branch. It contains specifications, starter templates, prompts, optional integrations, examples, validators and this wiki.

Your **game repository** is separate. The six starter files copied into it refer to that game. Never copy the framework's inherited root `AGENTS.md` into your game: that file belongs to the original full ADDF edition.

<a id="wiki-foundations--overview--the-three-non-negotiable-gates"></a>
### The three non-negotiable gates

| Gate | Human decides | Durable record |
| --- | --- | --- |
| **D — Design** | Meaningful design alternatives and the sprint's intended outcome | `DECISIONS.md` and `SPRINT.md` |
| **I — Implementation** | Exact files, commands, dependencies, side effects and plan revision | `PLAN.md` |
| **A — Acceptance** | Whether first-hand playtesting/review meets the sprint goal | `REVIEW.md` |

A conversational “sounds good” about a concept **is not** permission to change code. A passing test **is not** player acceptance.

<a id="wiki-foundations--overview--what-a-first-result-looks-like"></a>
### What a first result looks like

A user chooses a tiny dodge game. The agent compares direct versus accelerating movement, the person selects a style, and the agent drafts one sprint: move a placeholder duck in an arena and avoid one repeating obstacle. The agent shows exactly what it plans to change and asks for authorization. After implementation, the person plays, observes a readability problem and requests a small refinement. The sprint ends only with the person's verdict.

This is more useful than generating an entire untested game from one sentence.

<a id="wiki-foundations--overview--common-failures"></a>
### Common failures

**Too much process:** Require the full wiki before starting, or make the user fill every field. Instead, start with one question and let the agent draft files.

**Too little control:** Skip the dry-run approval for “obvious” changes. Instead, use a short exact plan.

**False progress:** Treat an AI's claim that a build works as evidence of gameplay feel. Instead, distinguish verified command output from a human observation.

<a id="wiki-foundations--philosophy"></a>
## Philosophy: Deep Reference, Small Runtime


ADDF Light Games retains original ADDF's **file-first memory, bounded roles and human approval** while reducing the number of documents and repetitive prompts needed to run an ordinary game-design sprint.

<a id="wiki-foundations--philosophy--when-to-use"></a>
### When to use

Read this when deciding whether the framework is too heavy, when explaining it to a class or team, or when considering a new rule that would add friction to a beginner's first session.

<a id="wiki-foundations--philosophy--principle-1-the-human-designs-the-experience"></a>
### Principle 1 — The human designs the experience

The agent can research camera options, prototype a movement controller and summarize playtest comments. It must not silently decide whether the game should be a puzzle or a shooter, whether acceleration is desirable, or whether a playable slice “feels good.” Those are meaningful human choices informed by evidence.

Not every variable name is a vote. **T0 routine** implementation details can be resolved by the agent inside an approved plan. **T1 significant** choices require a design decision. **T2 high-impact** matters—security, costs, destructive actions, public publishing—require stricter review and possibly separate special authorization.

<a id="wiki-foundations--philosophy--principle-2-learning-is-part-of-making"></a>
### Principle 2 — Learning is part of making

An agent should explain *why* the first sprint tests movement or feedback, not merely provide code. A learning checkpoint may ask the designer to predict whether instant movement will feel snappy or overly rigid, then compare that hypothesis with actual playtesting.

It must be relevant to the work. No artificial quizzes or compulsory theoretical detours.

<a id="wiki-foundations--philosophy--principle-3-evidence-beats-plausible-narration"></a>
### Principle 3 — Evidence beats plausible narration

Each important statement is **verified**, **inferred**, **proposed**, or **unknown**. An installed test script is not a passing test. A green test is not a successful manual playthrough. A model's fabricated “Human approved” field does not authorize anything.

Agent handoffs start from the project's files and check Git/worktree state where possible. Chat history is useful context but insufficient authority for a stale plan.

<a id="wiki-foundations--philosophy--principle-4-one-playable-slice-at-a-time"></a>
### Principle 4 — One playable slice at a time

A *slice* is a narrow, observable player experience. A full level, inventory, skill tree and save system in Sprint 001 would hide risks and make evaluation harder. Isolate the smallest experiment that tests the central unknown.

Ideas not needed now stay in `planning/BACKLOG.md`; they are not lost, nor automatically approved.

<a id="wiki-foundations--philosophy--principle-5-safety-isn-t-an-optional-advanced-feature"></a>
### Principle 5 — Safety isn't an optional advanced feature

The simple workflow retains three separate human gates: design, exact implementation authorization, and actual acceptance. Permission to run a terminal is not permission to run an arbitrary command. Permission to edit one file does not authorize a new package, API, deletion, deployment or network transfer.

The validator checks **internal file consistency** but cannot authenticate consent. This limitation is intentional and documented.

<a id="wiki-foundations--philosophy--principle-6-progressive-disclosure"></a>
### Principle 6 — Progressive disclosure

The normal path needs six persistent Markdown files and, when work is chosen, `SPRINT.md`, `PLAN.md`, `REVIEW.md`. Add architecture diagrams, asset licensing inventories, release records or cross-sprint risk logs **only when needed**.

A comprehensive wiki, generated manual and provider-specific skills can exist without burdening the user with all of them during onboarding.

<a id="wiki-foundations--philosophy--example-avoiding-false-autonomy"></a>
### Example: avoiding false autonomy

A student says: “Make enemy AI.” The agent asks which behavior should be observable in the first playtest, compares patrol-and-chase versus a stationary defender, and asks the student to choose. It writes acceptance criteria, then a narrow implementation plan. When the student says “I choose patrol,” the agent records Gate D **but does not code** until Gate I. Once the code is built, the student tries it and reports whether the chase is legible; the model does not award itself Gate A.

<a id="wiki-foundations--philosophy--common-failures"></a>
### Common failures

**Process theater:** Files are complete but nobody tested the mechanic. Recover by defining observable acceptance criteria.

**Agent overreach:** An adapter enables shell tools and assumes it may edit anything. Recover by checking the actual `PLAN.md` revision.

**Documentation overload:** A novice gets nine questionnaires. Recover with the first-session script and a default `unknown` value.

## ADDF Light Games vs. Original ADDF


This comparison is a **conceptual comparison of the current original ADDF v3.5 framework and the ADDF Light Games branch**, not a suggestion to overwrite or automatically merge them. The original repository's `main` branch remains the canonical full ADDF edition.

<a id="wiki-foundations--comparison--when-to-use"></a>
### When to use

Consult this before choosing a methodology, explaining the game-focused adaptation, adopting Light in an existing full-ADDF project, or deciding whether to add more governance.

<a id="wiki-foundations--comparison--side-by-side-comparison"></a>
### Side-by-side comparison

| Dimension | Original ADDF (v3.5) | ADDF Light Games |
| --- | --- | --- |
| **Primary domain** | General LLM-assisted software development | Games and interactive playable experiences |
| **Intended user** | Operators comfortable with a detailed, auditable engineering process | Solo makers, students, designers and small game teams seeking low-friction guidance |
| **Design goal** | Formal file-backed control across complex lifecycle and work scale | Preserve control while minimizing the *user's* process burden |
| **Public lifecycle** | Eight steps: Research; Design & Feasibility; Validation Gate; Architecture; Sprint Planning; Build & Test; Review & Reflection; Deploy/Maintain/Resume | Five stages: Research; Design/Ideation; Implement; Refine; Acceptance |
| **Operating boundaries** | Explicit Research Mode, Design Mode, Develop Mode | Same three distinct *capabilities*, with five player-facing lifecycle stages |
| **Sprint workflow** | Eleven-step controlled Sprint Loop, including dry run and several human checks | One bounded iteration with three human gates, plus scope-aware refinement |
| **Default project memory** | `AGENTS.md`, `DOMAIN.md`, `STATE.md`, `COMMANDS.md`, `SECURITY.md` and additional decision/question/risk/style files | Six persistent files: `AGENTS.md`, `SECURITY.md`, `GAME.md`, `STATE.md`, `DECISIONS.md`, `planning/BACKLOG.md` |
| **Game intent** | General domain is documented in `DOMAIN.md` | Player experience, core loop, design pillars and playable hypothesis in `GAME.md` |
| **Sprint documents** | Typically separate `requirements.md`, `blueprint.md`, `acceptance.md`, `dry_run.md`, implementation log, human review and retrospective | Three files: `SPRINT.md`, `PLAN.md`, `REVIEW.md` |
| **Research handling** | Dedicated research files, questions and risk tracking | Focused active sprint research; larger studies are optional |
| **Human design control** | Explicit validation/blueprint and design review | **Gate D** for consequential direction and acceptance criteria |
| **Code authorization** | Develop Mode starts with Permission Level 0 dry run and specific human authorization | **Gate I**, tied to exact plan revision, paths, commands, dependencies and side effects |
| **Outcome acceptance** | Human review, approval and retrospective within sprint governance | **Gate A**, requiring actual human gameplay/review; tests alone do not count |
| **Permission detail** | Formal Develop Mode permission levels and scale model | Core safe boundaries plus separate special approvals; advanced controls optional |
| **Onboarding** | Copy full blank starter kit and initialize more project-memory files | Copy six files or adopt an existing repo read-only; choose first sprint later |
| **User questioning** | Formal research/design workflows | Guided discovery: one consequential question at a time by default |
| **Learning focus** | Engineering rigor, repeatability and auditability | Those goals **plus explicit game-design learning and playtest predictions** |
| **Example deliverable** | General mini-task-tracker example and engineering artifacts | Dependency-free browser Duck Dodge pilot with real tests, plus onboarding/adoption exercises |
| **Model integrations** | Model-agnostic prompt catalog | Nine lifecycle prompts and optional Claude Code, Codex, OpenClaw skill adapters |
| **Automated validation** | Full-ADDF checklists and governance procedures | Python structural validator and branch-only CI; warns that human consent cannot be authenticated |
| **Documentation depth** | Extensive wiki and long consolidated reference | Extensive dedicated wiki and generated single-document manual, **without forcing every chapter into normal workflow** |
| **Suitable scale** | Broad work, multi-team delivery, governance-heavy/high-risk projects | Prototypes, learning, smaller game projects and bounded playable feature increments |
| **Relationship** | Independent canonical edition on `main` | Separate branch `ADDF_light_games`; **not** an automatic merge or replacement |

Original ADDF itself is adaptable to work scale. It is inaccurate to say it *always* requires every optional file for the smallest patch. The distinction here is that Light **codifies** a tiny default runtime around game-playable evidence.

<a id="wiki-foundations--comparison--what-is-deliberately-preserved"></a>
### What is deliberately preserved?

Both editions require durable project memory, role-aware write boundaries, a dry-run before changing implementation, explicit human authorization, honest test evidence and resumable handoffs. Light is **not a permissionless mode**.

<a id="wiki-foundations--comparison--what-is-deliberately-reduced"></a>
### What is deliberately reduced?

Light consolidates sprint artifacts and keeps optional risk, architecture, asset, feature and release records out of the first-time template. Rather than a complete project brief, it can start from one sentence and expand only after decisions are made.

That consolidation is a *navigation decision*, not permission to omit scope, source provenance, rollback, review history or security constraints.

<a id="wiki-foundations--comparison--choosing-an-edition"></a>
### Choosing an edition

Use **Light Games** if the immediate goal is to explore and validate playable behavior with a small team, to teach game mechanic/system/level design, or to build an incremental game prototype. Choose **original ADDF** when delivery requires detailed formal architecture, richer cross-team release governance, multiple risk tracks, or explicitly managed permission tiers.

A real existing project can migrate only via an **audited, human-approved mapping**; do not blindly rename its `DOMAIN.md` to `GAME.md` or delete historic sprint records.

## Core Concepts and How They Fit Together


ADDF Light Games consists of five interlocking concepts: **the game project**, **persistent project brain**, **bounded sprint**, **write capability**, and **human gate**. Confusing any pair of these is a common source of AI overreach.

<a id="wiki-foundations--core-concepts--when-to-use"></a>
### When to use

Use this when an agent seems to conflate an approved design with implementation permission, a branch with a sprint, or a technical test with actual human acceptance.

<a id="wiki-foundations--core-concepts--project-and-framework-are-different-things"></a>
### Project and framework are different things

The framework distribution supplies rules and starter files. The individual game's project repository contains the actual source, game intent, current state and real approval records. The framework's `spec/` files are authoritative for distribution templates, but a game's current human-approved `GAME.md` and decisions reflect the user's project-specific intentions.

The game engine is not the framework. A browser Canvas prototype, Phaser game, Godot project or Unity game may all follow the same decision and approval process.

<a id="wiki-foundations--core-concepts--project-brain"></a>
### Project brain

Six persistent files exist in a blank project: `SECURITY.md`, `AGENTS.md`, `GAME.md`, `STATE.md`, `DECISIONS.md`, `planning/BACKLOG.md`. They are intentionally small at first. The agent updates them as facts and choices become known.

`STATE.md` is a **summary view**, not independent proof of human permission. The exact consent source and plan revision must be recoverable from the relevant sprint record.

<a id="wiki-foundations--core-concepts--sprint-pack"></a>
### Sprint pack

One sprint has three files under `planning/sprints/sprint-NNN/`:

| File | Owns | Approval |
| --- | --- | --- |
| `SPRINT.md` | Goal, research, scope, design alternatives, learning checkpoint, `AC-##` criteria | Gate D |
| `PLAN.md` | Exact file operations, dependencies, commands, risks, test plan, implementation record | Gate I |
| `REVIEW.md` | Actual test outcomes, human observations, refinements, final verdict | Gate A |

A sprint represents a bounded, verifiable **learning or playable outcome**. A backlog item is only a candidate, not an approved sprint. Creating a Git branch is not a substitute for creating/approving the sprint documents.

<a id="wiki-foundations--core-concepts--stages-versus-capabilities"></a>
### Stages versus capabilities

**Stages** communicate what work the person and agent are doing: research, design, implement, refine, accept.

**Capabilities** govern file writes:
- Research: safe investigation and notes, no source changes.
- Design: project-brain and plan drafting, no source changes.
- Develop: changes only inside a human-approved exact `PLAN.md`.

An agent in the “Refine” stage may still need Develop capability and a valid Gate I to change code.

<a id="wiki-foundations--core-concepts--approval-versus-evidence"></a>
### Approval versus evidence

A successful Node test establishes a particular behavior in a known execution environment. It does not show that a person liked the control feel. A line in `PLAN.md` saying `gate_i_status: authorized` must be linked to a real human response; the Python validator can check internal coherence **but cannot authenticate authorship**.

A materially changed plan **invalidates** authorization tied to the older revision. Preserve the historical approval rather than overwriting it.

<a id="wiki-foundations--core-concepts--example-moving-a-duck"></a>
### Example: moving a duck

The backlog holds “Make movement responsive.” Sprint 001 narrows it to four-direction movement in a small arena. A design choice considers acceleration, Gate D records the selected feel. The plan lists an exact JavaScript file, test command and no dependencies. Gate I permits that revision only. The agent implements, verifies directional movement and presents a runnable game. The human tests and provides Gate A.

If the agent discovers a need for a new input package after starting, it **stops** and revises the plan instead of interpreting the initial authorization broadly.

<a id="wiki-foundations--core-concepts--common-failures"></a>
### Common failures

**Status as authority:** `STATE.md` says authorized but no consent source exists. Fail closed.

**Overgrown sprint:** A sprint bundles several untested systems. Split into testable slices.

**Lost evidence:** The agent stores all choices in chat only. Update `DECISIONS.md` and the sprint pack.

<a id="wiki-foundations--glossary"></a>
## Glossary


A concise shared vocabulary matters because an AI can otherwise treat “approve,” “test,” or “sprint” too loosely.

<a id="wiki-foundations--glossary--when-to-use"></a>
### When to use

Use this when a term in a prompt, review, agent handoff, or validator report is unclear.

| Term | Meaning in ADDF Light Games |
| --- | --- |
| **Acceptance criteria (`AC-##`)** | Observable checks written **before implementation**; each must have a corresponding `REVIEW.md` result |
| **Agent / assistant** | An AI providing research, drafting or authorized implementation; it does not become the human project owner |
| **Backlog (`B-###`)** | Future candidate outcomes and experiments, not implementation authorization |
| **Capability** | Research, Design, or Develop write boundary; separate from the five lifecycle stages |
| **Decision (`D-###`)** | Consequential human choice, including alternatives, rationale and future revisit trigger |
| **Dry run** | Proposed exact file operations, commands, dependencies, risks and tests in `PLAN.md`, performed **without code edits** |
| **Evidence** | Source, actual test result, inspectable artifact or human observation; classified as verified/inferred/proposed/unknown |
| **Gate D** | Human decides material design direction and relevant sprint acceptance goal |
| **Gate I** | Human explicitly authorizes a **specific current plan revision and scope**, before source edits |
| **Gate A** | Human evaluates the actual outcome via first-hand test/review and supplies acceptance verdict |
| **Human owner** | Person who approves significant design, authorization and acceptance; may delegate routine within-scope work |
| **Light** | Low-friction daily use with thorough reference docs, not reduced safety or a light-color variant |
| **Learning checkpoint** | A short explanation/prediction tied to a design tradeoff and later observation |
| **Material scope change** | New paths, commands, dependency, risk, external effect or meaningful behavior; requires a revised Gate I |
| **Optional module** | Advanced architecture, risk, feature/release or asset tracking added only when necessary |
| **Plan revision (`rN`)** | Version of the technical authorization scope; old consent does not cover a materially changed revision |
| **Playable slice** | Small, observable player action and game response that can be evaluated in one bounded iteration |
| **Project brain** | Six persistent Markdown files recording safe rules, game intent, decisions, state and backlog |
| **Refinement round (`round-N`)** | Preserved record of feedback, correction, retest and verdict in `REVIEW.md` |
| **Research spike** | Bounded investigation with a specific evidence deliverable, not an automatically playable feature |
| **Sprint** | One bounded game outcome or focused research experiment, with `SPRINT.md`, `PLAN.md`, `REVIEW.md` once active |
| **Stage** | User-facing Research, Design/Ideation, Implement, Refine, Acceptance |
| **State/status** | Current operational position in `STATE.md`; status must match the stage and actual gate evidence |
| **Synthetic fixture** | Invented test data, which does not constitute a real person's approval or playtest |
| **T0 / T1 / T2** | Routine detail / consequential design choice / high-impact safety or cost decision |
| **Worktree** | Actual source-control checkout and uncommitted state; must be inspected before risky edits |

<a id="wiki-foundations--glossary--applying-terms-correctly"></a>
### Applying terms correctly

“Design approved” means Gate D, not permission to write source. “Plan authorized” means Gate I for exactly one revision/scope, not permission to deploy. “Automated test passed” is evidence, not Gate A. “Accepted with conditions” preserves those conditions and cannot silently become an unconditional release.

<a id="wiki-foundations--glossary--common-failures"></a>
### Common failures

**Generic yes:** The human says “yes” but the agent cannot identify which revision and scope was displayed. Keep Gate I pending and ask a precise question.

**Invented test:** A model narrates “I opened the game” without tool evidence or the person's report. Mark unverified.

**Conflicting state:** The plan shows r2, the state refers to r1. Stop and reconcile.

## Install the Minimal Starter Kit


ADDF Light Games has no obligatory CLI installer. Installation means copying **six Markdown files into a new game-project folder**, then using a prompt to begin guided discovery.

<a id="wiki-guides--install--when-to-use"></a>
### When to use

Use this for a **new** project. If you already have code or a root `AGENTS.md`, follow [existing-project adoption](#wiki-guides--existing-project) instead; do not overwrite it.

<a id="wiki-guides--install--before-you-begin"></a>
### Before you begin

You need a folder where you can create files and an AI assistant. You do **not** need Unity, Godot, Phaser, OpenClaw, a credit card, cloud hosting or a complete concept to start.

Confirm you are viewing the `ADDF_light_games` branch of the framework, not the original `main`. The inherited `starter-kit/blank/` directory belongs to **full ADDF**. Light's six files live under `starter-kit/minimal/`.

<a id="wiki-guides--install--copy-these-files"></a>
### Copy these files

```text
your-game/
├── AGENTS.md
├── SECURITY.md
├── GAME.md
├── STATE.md
├── DECISIONS.md
└── planning/
    └── BACKLOG.md
```

Source: [Light starter kit](https://github.com/Walabrolu4/Autonomous-Duck-Development-Framework/blob/ADDF_light_games/starter-kit/LIGHT_GAMES.md) and [minimal folder](https://github.com/Walabrolu4/Autonomous-Duck-Development-Framework/tree/ADDF_light_games/starter-kit/minimal).

The initial `STATE.md` reads `lifecycle_stage: research`, `sprint_status: discovering`, `active_sprint: none`, `authorized: no`. That's correct. The game title, engine and prototype goal may be `unknown`.

**Do not copy the three sprint files yet.** They remain distribution templates under `starter-kit/sprint-template/` until the human chooses the first milestone.

<a id="wiki-guides--install--initial-verification"></a>
### Initial verification

1. Open `SECURITY.md` and make sure its excluded paths and network restrictions fit your environment. Never add real secret values to the document.
2. Open `AGENTS.md`; it must describe Gate D, Gate I and Gate A and the roles' write boundaries.
3. Open `STATE.md`; confirm no implementation has been authorized.
4. Make sure `GAME.md` still labels unselected ideas as unknown, rather than falsely chosen.
5. Optionally run the Python validator after Stage 6 if you have Python installed:

```bash
python3 /path/to/framework/scripts/validate_light.py /path/to/your-game
```

This is a **read-only** structural check. It is not a permission grant and cannot prove human consent.

<a id="wiki-guides--install--optional-integrations"></a>
### Optional integrations

Claude Code can load a project skill under `.claude/skills/addf-light-games/SKILL.md`; Codex can load one under `.agents/skills/addf-light-games/SKILL.md`; OpenClaw is optional and requires its own deliberately configured workspace. Install these **only if you use that host**. The core six files are sufficient for manual chat workflows.

<a id="wiki-guides--install--example-first-few-minutes"></a>
### Example: first few minutes

The user says, “I want a small browser game but don't know what kind.” The agent reads safe project context and offers a dodge, path-puzzle or tactical encounter concept. The user selects one. The agent drafts a small player-facing goal, not game code. After the human chooses a milestone, it creates the sprint triplet and requests the two appropriate approvals.

<a id="wiki-guides--install--common-failures"></a>
### Common failures

**Wrong source:** Copying the framework's root `AGENTS.md` or original full kit. Copy only the six Light `minimal/` files.

**Premature paperwork:** Filling out a future Sprint 001 with fabricated decisions before the user has chosen anything. Leave it absent.

**Unsafe existing repo:** Overwriting another project's instructions. Run the read-only adoption audit first.

## Your First ADDF Light Games Session


The first session should feel like a short game-design conversation, **not a form**. A user may start with no idea; the agent must provide useful choices without demanding a novel-length GDD.

<a id="wiki-guides--first-session--when-to-use"></a>
### When to use

Use this after copying the six starter files, or when showing a new game-design student how to ask an AI assistant for thoughtful help instead of one-shot generation.

<a id="wiki-guides--first-session--before-the-conversation"></a>
### Before the conversation

The agent reads `SECURITY.md` first, then `AGENTS.md` and `STATE.md`. It may read `GAME.md`, `DECISIONS.md` and the backlog when necessary. If it has no file access, the user can provide safe excerpts, and the agent must label its edits **proposed** instead of claiming it saved them.

Never provide API keys, private accounts or hidden credentials to get the session started.

<a id="wiki-guides--first-session--the-first-prompt"></a>
### The first prompt

> Use ADDF Light Games. Read the project's SECURITY.md, AGENTS.md and STATE.md before exploring other files. Help me find **one small playable outcome** by asking one meaningful question at a time. Explain major design tradeoffs, label assumptions, and maintain the project brain if permitted. Do not edit game code, install packages or publish anything. Stop before implementation and show me an exact plan for my approval.

Then add your idea—or simply say, “I have no idea what to make.”

<a id="wiki-guides--first-session--session-sequence"></a>
### Session sequence

1. **Orient:** Establish whether the user has no idea, one sentence or an existing game. Report known versus inferred details.
2. **Discover:** Offer two or three genuinely distinct small ideas when needed. Each should have a player action, a system response and a feasible first slice.
3. **Learn:** Compare one consequential tradeoff such as instant movement versus acceleration, or a fixed obstacle versus a moving one.
4. **Choose:** Let the person select or defer. Record real decisions in `DECISIONS.md`; unanswered questions remain pending.
5. **Propose a sprint:** One observable goal, in/out scope, testing method and minimal risk. Move extra ideas to the backlog.
6. **Gate D:** Obtain an actual human decision on significant game direction and acceptance criteria.
7. **Prepare a dry run:** Draft `PLAN.md` with exact paths, commands, dependencies, risk and rollback.
8. **Gate I:** Stop and ask the human to authorize the actual plan revision. Only after explicit authorization may implementation begin.
9. **Gate A later:** The human plays the resulting game; automated test success is not acceptance.

For most first sessions, stopping after steps 1–6 is perfectly useful.

<a id="wiki-guides--first-session--what-the-agent-writes"></a>
### What the agent writes

The agent updates `GAME.md` only for actual intended experience or clearly proposed ideas, allocates `D-###` entries for significant choices, and puts future candidates in `planning/BACKLOG.md`.

Only after selecting an actual milestone does it create `planning/sprints/sprint-001/` from the three template files. It can draft technical assumptions and tests, but it cannot invent a past consent record.

<a id="wiki-guides--first-session--example-conversation"></a>
### Example conversation

**User:** “I want something about movement.”

**Agent:** “Two small first slices: a duck avoiding horizontal obstacles, or a character jumping between two platforms. The first isolates movement clarity; the second adds timing and gravity. Which interaction do you want to study?”

**User:** “Duck dodge, simple directional controls.”

**Agent:** “We can start with immediate movement or acceleration. Immediate movement makes collision and responsiveness easier to evaluate; acceleration might feel more expressive but needs tuning. Which do you prefer?”

**User:** “Immediate for Sprint 001.”

That is a real design choice in the conversation. It is **not yet Gate I**. The agent should now show the exact first-sprint plan and ask permission before building.

<a id="wiki-guides--first-session--closing-the-session"></a>
### Closing the session

Summarize last verified status, what documents changed, which gates are pending, and **one next action**. Update `STATE.md` if tools and permission allow. Next session begins with the [resumption protocol](#wiki-agents--handoff) rather than trusting a model's memory.

<a id="wiki-guides--first-session--common-failures"></a>
### Common failures

**Too many questions:** Ask one impactful question, not ten unrelated preferences.

**Overeager agent:** It generates the game immediately after the user selects a genre. Stop at the dry-run gate.

**Pretend state:** A chat assistant claims it edited files without file tools. Provide a proposed diff instead.

<a id="wiki-guides--from-zero"></a>
## Starting Without a Game Idea


“No idea yet” is an **acceptable and productive** initial state. Light's discovery protocol exists precisely so the human can learn and choose without having to supply an entire design brief.

<a id="wiki-guides--from-zero--when-to-use"></a>
### When to use

Use this for new designers, a classroom warm-up, exploratory prototypes and users who know they want to make a game but cannot name a mechanic.

<a id="wiki-guides--from-zero--discovery-procedure"></a>
### Discovery procedure

**Step 1 — Ask one preference, not a questionnaire.** For example: “Would you rather make something about movement, solving a puzzle, or tactical decisions—or should I suggest three options?”

**Step 2 — Offer 2–3 differentiated concepts.** Each option should communicate:
- the core player action;
- what the system does in response;
- the feeling or design principle it might explore;
- one minimum playable experiment;
- the main uncertainty.

**Step 3 — Explain one design fork.** If the user chooses movement, compare direct versus momentum-based control. If they choose puzzles, compare open exploration versus a sequence of fixed challenges. The agent recommends a reversible starting experiment and says why.

**Step 4 — Record the actual choice.** Update `GAME.md` and allocate a `D-###` record when the choice is consequential. If the user is unsure, mark the choice deferred and offer a small research spike.

**Step 5 — Select the first slice.** Propose an observable milestone, such as “Move a placeholder in a visible arena and survive one obstacle.” Do not promise a complete scoring system, art style, levels, save system and multiplayer in one step.

**Step 6 — Gate D then Gate I.** Significant design approval is recorded separately from permission to edit exact files.

<a id="wiki-guides--from-zero--worked-example"></a>
### Worked example

| Option | Player verb | Smallest playable slice | Primary learning |
| --- | --- | --- | --- |
| Dodge the hazard | Move / avoid | One avatar, one repeating moving obstacle, collision and restart | Control feel and clarity |
| Connect the path | Rotate / connect | Rotate tiles to join start and goal | Local feedback and puzzle legibility |
| Two-unit tactics | Select / choose | Two controllable units and one visible conflict resolution | Rules, state and meaningful choice |

A user picks the puzzle. The agent might ask: “Should a tile snap in quarter turns or rotate freely? Quarter turns are simpler and make valid connections unambiguous. Which first experiment should we build?” The user decides or asks for a side-by-side prototype.

A good first `SPRINT.md` states only the chosen action, measurable outcome, in/out scope, learning objective and acceptance checks. A good `PLAN.md` names the exact files and commands needed to test that outcome.

<a id="wiki-guides--from-zero--if-the-user-cannot-choose"></a>
### If the user cannot choose

Do not force a direction or pretend an AI recommendation is a human decision. Offer a reversible 15-minute **design exercise** or focused no-code research. A formal code-producing prototype still requires an authorized sprint plan.

<a id="wiki-guides--from-zero--what-should-not-happen"></a>
### What should not happen

- No automatic engine selection based on the AI's comfort.
- No full asset pipeline or monetization strategy before the player verb is known.
- No prefilled “human approved” decision record.
- No multi-page list of aesthetic preferences that delays the first useful test.

<a id="wiki-guides--from-zero--common-failures"></a>
### Common failures

**Options differ only in theme:** “Dodge asteroids,” “dodge cars,” “dodge fruit.” Offer different **interaction systems**, not merely art skins.

**Unbounded ideation:** A hundred ideas without choosing. Limit to the smallest decision that unlocks a concrete sprint.

**Agent chooses for the student:** The assistant may recommend, but must record the user's actual preference.

<a id="wiki-guides--from-idea"></a>
## Starting With a One-Sentence Idea


An idea such as “a fishing game where the weather changes the fish” is enough to begin. The agent should **unpack it carefully**, not treat its guesses as settled facts or build an enormous project from it.

<a id="wiki-guides--from-idea--when-to-use"></a>
### When to use

Use this when the user knows a fantasy, setting, core interaction or desired emotion but has not chosen the engine, control model, scope or technical system.

<a id="wiki-guides--from-idea--three-column-understanding"></a>
### Three-column understanding

The first agent response distinguishes:

| Category | Example for a weather-driven fishing game |
| --- | --- |
| **Known** | Fishing is the main activity; weather affects fish in some way |
| **Inferred** | The player may cast a line; fish may have spawn rules; likely needs feedback |
| **Unknown** | What weather changes; platform/input; arcade vs simulation; intended first slice |

Do not convert inferred mechanics into `GAME.md` pillars without user confirmation.

<a id="wiki-guides--from-idea--narrow-to-a-testable-core"></a>
### Narrow to a testable core

Ask: “What should the player be able to do in the first five minutes of testing?” A useful slice could be: **press a button to cast a line; a simple rain toggle changes the visible chance of a fish appearing**. This tests the weather-mechanic relationship with placeholder art and no inventory/economy.

Explain alternatives that actually affect the experience. For example, “weather changes bite probability” versus “weather changes fish movement” asks for a different test and different technical plan.

Put boats, characters, maps, online co-op and nuanced ecosystems into the backlog until relevant.

<a id="wiki-guides--from-idea--research-when-needed"></a>
### Research when needed

If a claim about a target game engine or platform might change feasibility, check current authoritative documentation or perform a small bounded experiment. Record sources and unknowns. Never fabricate an engine feature, benchmark or API call.

If the idea needs expensive hardware, credentials, a data source or paid service, propose an offline substitute for the first slice or request the necessary separate authorization.

<a id="wiki-guides--from-idea--write-the-design-record"></a>
### Write the design record

The agent should maintain:
- `GAME.md` — confirmed player action, intended experience, constraints and playable hypothesis;
- `DECISIONS.md` — meaningful human selection among weather-mechanic alternatives;
- `planning/BACKLOG.md` — deferred features;
- `SPRINT.md` — one selected outcome, in/out scope and `AC-##` checks.

Then prepare `PLAN.md` with exact implementation operations and seek Gate I. Do not preinstall dependencies while “doing research.”

<a id="wiki-guides--from-idea--example-acceptance-criteria"></a>
### Example acceptance criteria

**AC-01:** The player can initiate a cast with a clearly labeled input; the game shows the action.

**AC-02:** Toggling rain changes the observed in-game indicator and affects one defined fishing rule.

**AC-03:** Reset returns weather and fishing state to the chosen baseline.

The criteria should specify methods, environment and evidence when actual sprint documents are written. A player must test whether the relation is understandable even if deterministic unit checks pass.

<a id="wiki-guides--from-idea--common-failures"></a>
### Common failures

**Scope inflation:** AI adds crafting, inventory and fishing economy. Recover by isolating one observable cause/effect.

**False consensus:** It assumes realism, difficulty or graphics without user choice. Mark such matters unknown.

**Early technology lock-in:** “Fishing implies Unity.” The framework is engine-agnostic; choose tools based on the actual slice.

## Adopt Light in an Existing Game Project


An existing repo has history, human-owned design choices, source files, build constraints and possibly an `AGENTS.md` that defines permissions. Light should **integrate** with that reality, not overwrite it.

<a id="wiki-guides--existing-project--when-to-use"></a>
### When to use

Use this for an ongoing Phaser, Unity, Godot, Unreal, web or custom-engine project; for a repo previously using original ADDF; or for a classroom project with established files.

<a id="wiki-guides--existing-project--phase-1-read-only-audit"></a>
### Phase 1 — Read-only audit

Before opening arbitrary files, identify likely secret paths and excluded data. Read relevant safe files and list:
- engine/language and **verified** project structure;
- existing design intent and gameplay systems;
- run/build/test commands, distinguishing actual execution from documentation;
- `AGENTS.md`, `CLAUDE.md` or other project instructions that might conflict;
- current branch/worktree, uncommitted work and important backups;
- active issues, risks and unknowns.

Do not run installers, apply a starter kit, change Git settings, rename files or edit game source during the audit.

<a id="wiki-guides--existing-project--phase-2-map-without-erasing"></a>
### Phase 2 — Map without erasing

| Existing document | Possible Light destination | Treatment |
| --- | --- | --- |
| GDD, design brief, README | `GAME.md` | Summarize confirmed intent; preserve original |
| Existing agent instruction file | `AGENTS.md` | Review conflict; **never blindly overwrite** |
| Roadmap or issue list | `planning/BACKLOG.md` | Map candidates with history |
| Decisions and playtest notes | `DECISIONS.md` / `REVIEW.md` | Preserve actual sources and past verdicts |
| Existing security policy | `SECURITY.md` | Retain stricter exclusions |
| Prior full-ADDF sprint files | Light sprint triplet (optional migration) | Keep originals; map conceptual responsibilities |
| Source/config/assets | Remain as-is | No adoption-time changes by default |

The Stage 5 [existing-project fixture](https://github.com/Walabrolu4/Autonomous-Duck-Development-Framework/blob/ADDF_light_games/examples/existing-project/README.md) illustrates an `AGENTS.md` conflict, a read-only audit and a proposal to **merge** instructions instead of replacing them.

<a id="wiki-guides--existing-project--phase-3-proposed-migration-plan"></a>
### Phase 3 — Proposed migration plan

Before a single adoption write, identify exact paths to create/modify/move/delete, what content would be copied or reinterpreted, impacts on existing rules, potential data loss, rollback and the branch/worktree where changes would occur.

The human explicitly reviews that migration scope. General interest in Light does not authorize replacement of existing project instructions or code. Migrating project-brain documents is distinct from the Gate I needed for subsequent game implementation.

<a id="wiki-guides--existing-project--phase-4-safe-initial-state"></a>
### Phase 4 — Safe initial state

Once approved, create the minimal files where genuinely missing and record `project_origin: existing-project`. Start Light `STATE.md` in `research` / `discovering`, `authorized: no`, unless there is verifiable *current* Light sprint authorization. Existing code does not imply ongoing Gate I.

Choose a modest first task: a reproducible bug, a new playtest, a single mechanic or a research spike. Draft the sprint pack only after the human selects it.

<a id="wiki-guides--existing-project--verify-the-adoption"></a>
### Verify the adoption

Compare the actual diff against the migration plan. Confirm old GDD, source, Git history and permissions remain accessible. If a file was overwritten accidentally, stop, preserve the diff and seek human instructions on restoring it. Do not force-reset uncommitted work.

<a id="wiki-guides--existing-project--common-failures"></a>
### Common failures

**Blind copy:** Overwriting a rich `AGENTS.md` with the Light template. Use a reviewed merge.

**Fabricated test:** Assuming an existing project builds because a README contains a command. Mark not verified until run under proper permission.

**Silent mode migration:** Converting original ADDF approval levels into new Gate I without checking whether consent still applies. Keep old records, re-approve current scope.

<a id="wiki-guides--quick-reference"></a>
## Quick Reference: One Sprint at a Glance


This is the **one-page operational companion** to the full manual. Use it during a work session instead of reading the entire wiki repeatedly.

<a id="wiki-guides--quick-reference--when-to-use"></a>
### When to use

Use it when deciding what prompt to run next, which file the agent should update, what you must personally approve and when to stop.

<a id="wiki-guides--quick-reference--current-state-next-action"></a>
### Current state → next action

| Status in `STATE.md` | Agent action | Human action |
| --- | --- | --- |
| `discovering` | Summarize known/unknown; ask one question | Choose concept or request options |
| `designing` | Propose one slice, research, tradeoffs and `AC-##` | Decide meaningful direction (Gate D) |
| `awaiting_approval` | Show exact `PLAN.md` revision, paths, commands and risks | Explicitly authorize or revise (Gate I) |
| `implementing` | Change **only** approved source and log evidence | Review deviations if any |
| `refining` | Diagnose observed defect; check existing authorization | Choose correction or approve revised scope |
| `awaiting_acceptance` | Provide tested artifact, limitations and playtest steps | Play/review and provide Gate A |
| `accepted` | Preserve verdict, retro and backlog handoff | Choose next sprint if desired |
| `rejected` | Preserve rejection; propose safe direction | Decide revise/abandon |
| `paused` | Record blocker, last safe state and resume requirements | Supply needed authorization or context |

**The stage** is a separate field: research/design/implement/refine/acceptance. Status and stage must agree with the workflow contract.

<a id="wiki-guides--quick-reference--files-you-will-see"></a>
### Files you will see

```text
AGENTS.md         agent conduct / role boundaries
SECURITY.md       prohibited reads, tools, external effects
GAME.md           chosen player experience and constraints
STATE.md          current verified status, next action, gates
DECISIONS.md      actual material human choices
planning/BACKLOG.md candidates and deferred ideas
planning/sprints/sprint-NNN/
  SPRINT.md       goal, tradeoffs, acceptance criteria, Gate D
  PLAN.md         dry run, operations, commands, Gate I
  REVIEW.md       real results, playtest and Gate A
```

<a id="wiki-guides--quick-reference--the-three-questions-to-ask-before-authorizing-work"></a>
### The three questions to ask before authorizing work

**Design:** Is the player action/outcome clear, and do I actually choose this approach?

**Implementation:** Have I seen *exactly* which files/commands/dependencies/side effects this plan revision permits?

**Acceptance:** Have I actually played or inspected the result and reported my verdict, rather than trusting a green test?

<a id="wiki-guides--quick-reference--a-quick-stop-checklist"></a>
### A quick “stop” checklist

Stop before edits if:
- the current plan revision isn't explicitly authorized by you;
- a new path, dependency, command, paid service, privacy risk or deployment is needed;
- the worktree/source state conflicts with the plan;
- the assistant claims an approval you cannot verify;
- a human review has not occurred but status says `accepted`.

<a id="wiki-guides--quick-reference--commands"></a>
### Commands

To check your own project file structure from the Light framework repository:

```bash
python3 scripts/validate_light.py /path/to/your-game
```

To check the distributed unstarted starter kit:

```bash
python3 scripts/validate_light.py starter-kit/minimal --mode template --sprint-template starter-kit/sprint-template
```

A PASS means **structural consistency only**, not authenticated human consent.

<a id="wiki-guides--quick-reference--common-failures"></a>
### Common failures

**Blind prompt chaining:** Automatically run START→IMPLEMENT. Pick prompt based on verified state and stop at each human gate.

**Routine overload:** Require permission for trivial variable names. Let agents choose T0 details within scope.

<a id="wiki-lifecycle--index"></a>
## The Five-Stage Game Development Lifecycle


Every ADDF Light Games sprint works toward a **small, verifiable player-facing outcome**. The five stages are Research → Design / Ideation → Implement → Refine → Acceptance. They describe what the user experiences, while Research/Design/Develop *capabilities* determine which files an agent may write.

<a id="wiki-lifecycle--index--when-to-use"></a>
### When to use

Read when starting a sprint, training an agent, deciding a next prompt, or reconciling a status that doesn't match the current work.

<a id="wiki-lifecycle--index--lifecycle-map"></a>
### Lifecycle map

| Stage | Primary question | Persistent work | Exit |
| --- | --- | --- | --- |
| **Research** | What don't we yet know, and why does it matter? | Evidence, questions, game hypothesis | Enough information to propose an experiment/decision |
| **Design / Ideation** | What exact player behavior and test will this sprint target? | `SPRINT.md`, decisions, criteria, learning checkpoint | Human Gate D resolved or validly not required |
| **Implement** | What exact files and commands may be changed? | Approved `PLAN.md`, code/tests/assets, execution record | Report actual evidence or a blocker |
| **Refine** | What did the test/playtest reveal and what should change? | `REVIEW.md` rounds, bounded corrections, revised plan if needed | Retest ready or ask for new scope approval |
| **Acceptance** | Does the real outcome meet the human's expectations? | Criterion results, human verdict, retrospective | Human Gate A, or return to refinement/rejection/pause |

A sprint can loop from refinement to design when the intended experience changes. The workflow is not a waterfall of huge milestones.

<a id="wiki-lifecycle--index--status-is-not-the-same-as-stage"></a>
### Status is not the same as stage

`STATE.md` also records one **sprint status**: `discovering`, `designing`, `awaiting_approval`, `implementing`, `refining`, `awaiting_acceptance`, `accepted`, `rejected`, `paused`. For example, `awaiting_approval` is a *status* during Design while the human evaluates a technical plan.

Formal allowed transitions and paused-state recovery are defined in the normative [Workflow States specification](https://github.com/Walabrolu4/Autonomous-Duck-Development-Framework/blob/ADDF_light_games/spec/WORKFLOW_STATES.md). Do not invent a new status just to describe a particular game-engine task.

<a id="wiki-lifecycle--index--the-permission-rule"></a>
### The permission rule

Research and Design may update permitted project-brain/sprint-planning Markdown; **they do not change game code, tests, assets, manifests or deployments**. Develop may alter only explicitly approved paths and commands after Gate I. A “Refine” stage does not waive this: code corrections still require valid Develop authorization.

The three gates are not interchangeable:
- Gate D: meaningful game design direction;
- Gate I: exact implementation plan revision;
- Gate A: first-hand human evaluation.

<a id="wiki-lifecycle--index--a-complete-example"></a>
### A complete example

A user wants a tiny obstacle-dodging game. Research checks whether immediate controls and simple collision are feasible in a browser. Design narrows to one duck, one obstacle type and a restart, with `AC-01` to `AC-03`. The human selects immediate movement (Gate D). The agent proposes three source files, a unit test and an authorized Node command; the human approves that exact plan (Gate I). Implementation yields a runnable arena and test results. The human reports the red obstacle is too hard to notice, so refinement investigates color contrast and proposes an in-scope change or revised plan. The user finally retests and gives Gate A.

If tests pass but the user hasn't played, the proper status is `awaiting_acceptance`, **not** `accepted`.

<a id="wiki-lifecycle--index--common-failures"></a>
### Common failures

**Stage drift:** The agent starts coding while `STATE.md` still says `designing` with no Gate I. Stop and reconcile.

**Automatic acceptance:** The coding agent marks the sprint complete because CI passed. Request actual user review.

**New feature as “refinement”:** A gameplay change creates a new system beyond the approved scope. Return to Design or backlog instead.

<a id="wiki-lifecycle--research"></a>
## Stage 1 — Research


Research is a focused investigation of uncertainty that could change the next game-design or engineering decision. It is **not** permission to begin an unbounded technical implementation.

<a id="wiki-lifecycle--research--when-to-use"></a>
### When to use

Use Research when the idea is vague, a control model is unclear, a target engine/API may be unsupported, a performance constraint matters or a playtest exposed an unknown.

<a id="wiki-lifecycle--research--inputs-and-source-discipline"></a>
### Inputs and source discipline

Start with the safe project brain and the current question: `GAME.md`, `DECISIONS.md`, optional current `SPRINT.md`, the project's permitted source and actual documentation.

For each meaningful factual finding, record:
- **Question:** What would change our decision?
- **Evidence:** A specific source URL, repository artifact, versioned documentation or actual measurement.
- **Confidence:** Verified, inferred, proposed or unknown.
- **Tradeoff:** How the evidence affects player experience, scope or complexity.
- **Next action:** Choice, focused experiment, or known blocker.

No source? Say *not verified* and describe how to check; don't fabricate benchmark numbers, platform support or citations.

<a id="wiki-lifecycle--research--research-should-be-bounded"></a>
### Research should be bounded

Ask whether the uncertainty can be resolved before committing to a sprint. One example: “Can keyboard and touch inputs drive the same movement function in a simple browser prototype?” This can be answered with documentation or a **read-only** code inspection. If answering requires a new runtime script, package installation or experiment that edits game files, write a plan and obtain Gate I first.

A **formal research-spike sprint** still uses `SPRINT.md`, `PLAN.md`, `REVIEW.md`, and its Gate I is scoped to the actual research operations, even when no source code is authorized. Pre-sprint read-only discovery doesn't need a fictional Gate I.

<a id="wiki-lifecycle--research--outputs"></a>
### Outputs

Focus important findings in `SPRINT.md` under Research and evidence when the sprint exists. Project-wide unknowns may be summarized in `STATE.md` or the backlog. A separate `research/` folder is optional when material no longer fits a sprint.

Present the person with **two or three feasible alternatives when genuine choices exist**, a reasoned recommendation and one consequential question.

<a id="wiki-lifecycle--research--example-movement-model"></a>
### Example: movement model

The agent compares:
- **Direct velocity:** immediate response, simple to test, possible abrupt feel;
- **Acceleration:** nuanced feel, requires tuning and more careful testing.

It might recommend direct movement for Sprint 001 because the first experiment is about obstacle legibility rather than motion physics. That recommendation is still **proposed**, not human-approved.

If the user says “I'm undecided,” offer a reversible pair of trials only after describing their file scope and obtaining authorization for any code.

<a id="wiki-lifecycle--research--exit-criteria"></a>
### Exit criteria

Research is ready to advance when the problem and main unknown are clear, evidence/uncertainty is labeled, significant alternatives are visible and a meaningful decision or testable hypothesis can be proposed. It is not necessary to know every implementation detail.

<a id="wiki-lifecycle--research--common-failures"></a>
### Common failures

**Research rabbit hole:** Reading fifty tutorials without narrowing a decision. Stop at the first material uncertainty.

**Assumption laundering:** “The engine supports this” without version/source. Mark unknown.

**Research bypass:** Running an unapproved install command because “it's only a spike.” Plan actual side effects first.

<a id="wiki-lifecycle--design"></a>
## Stage 2 — Design and Ideation


Design turns possibilities into **one bounded, testable gameplay outcome**. The agent facilitates and documents; the human owns material creative direction.

<a id="wiki-lifecycle--design--when-to-use"></a>
### When to use

Use once there is enough context to propose an observable action, game-system response and acceptance test—or when a failed prototype reveals that the intended experience needs to change.

<a id="wiki-lifecycle--design--design-brief-for-one-slice"></a>
### Design brief for one slice

A useful sprint brief answers:
1. **Player verb:** What does a player do?
2. **System response:** What happens in the game?
3. **Feeling or insight:** What should the player perceive or learn?
4. **Scope in/out:** What precisely isn't being built yet?
5. **Learning checkpoint:** Which mechanic/system tradeoff deserves explanation and a prediction?
6. **Acceptance criteria:** Which observable checks will determine whether the slice works?

If no significant design fork exists, document `gate_d_status: not_required` with a specific reason. Do not invent a second option to create artificial approval paperwork.

<a id="wiki-lifecycle--design--design-alternatives-and-gate-d"></a>
### Design alternatives and Gate D

A consequential choice deserves two genuine alternatives and tradeoffs. Examples:
- Movement is **instant** or **inertial**;
- Enemy reaction is **line-of-sight chase** or **proximity trigger**;
- Level learning happens in a **safe introduction** or a **high-pressure first encounter**.

Show the recommendation as advice, not a committed decision. Record the user's actual choice in `DECISIONS.md` and `SPRINT.md`, with rationale and conditions. A design approval **does not** permit writing code.

<a id="wiki-lifecycle--design--create-the-sprint-pack-at-the-right-time"></a>
### Create the sprint pack at the right time

Only after a real milestone is selected should the agent copy `SPRINT.md`, `PLAN.md`, and `REVIEW.md` templates into `planning/sprints/sprint-NNN/`. The agent can fill planning documents without user having to type entire schemas.

`SPRINT.md` defines the intended behavior and actual `AC-##` entries **before source implementation**. Each criterion specifies test method, setup/input, observable pass condition, evidence to capture and whether it blocks release.

<a id="wiki-lifecycle--design--example-a-dodge-prototype"></a>
### Example: a dodge prototype

The human approves a 2D browser slice:
- move a duck in four directions;
- avoid one type of moving obstacle;
- hit ends the attempt, restart begins again.

**Out of scope:** sounds, scoring service, level editor, multiplayer, art generator. **Learning checkpoint:** predicted difference between instantaneous and accelerating movement.

`AC-01` tests input response and arena bounds. `AC-02` tests collision/game-over visibility. `AC-03` tests restart. The person should still judge actual readability and feel during later acceptance.

<a id="wiki-lifecycle--design--exit-criteria"></a>
### Exit criteria

The design stage is ready for technical planning when selected scope, player behavior, significant choices, risk assumptions and criteria are explicit. The agent then drafts `PLAN.md` and seeks **Gate I** separately.

Do not allow “we agree on the game” to stand in for authorization of unreviewed paths or downloads.

<a id="wiki-lifecycle--design--common-failures"></a>
### Common failures

**Large invisible requirement:** “Create a fun game.” Specify what the player can do and observe.

**Design by agent default:** Select platform or art style without acknowledging the user didn't choose.

**Acceptance after implementation:** Define `AC-##` only when code is done. Reverse the order and obtain meaningful pre-implementation checks.

<a id="wiki-lifecycle--implement"></a>
## Stage 3 — Implement


Implementation is the **only stage that may actually change game source, tests, scenes, assets or dependencies**, and only while a specific **Gate I** authorization is valid.

<a id="wiki-lifecycle--implement--when-to-use"></a>
### When to use

Use when the human has reviewed the exact current `PLAN.md` revision and expressly permitted its operations. Do not invoke implementation simply because design looks ready, the shell works or a previous chat says “continue.”

<a id="wiki-lifecycle--implement--preconditions"></a>
### Preconditions

Read `SECURITY.md`, `AGENTS.md`, `STATE.md`, the active `SPRINT.md`, `PLAN.md`, and relevant decisions. Verify:
- active `sprint-NNN` and selected `AC-##`;
- Gate D for meaningful design (or justified not-required);
- plan file revision, exact operations, dependencies and commands;
- **real human approval** of that same revision and scope, with conditions;
- current worktree/source baseline and conflicting human changes;
- special approval for destructive, paid, sensitive, public or other external effects.

Missing proof means **stop**, not reinterpret the plan as authorized.

<a id="wiki-lifecycle--implement--execution-sequence"></a>
### Execution sequence

1. Inspect only the approved files and environment; check whether original assumptions still hold.
2. Implement the **smallest change** supporting one acceptance criterion.
3. Execute only approved test/build commands in their specified working directories.
4. Log actual changed paths, command outcomes, failures, versions when known and unexpected behavior.
5. Compare the diff with the approved operation list. Do not assume a green build implies no unauthorized change.
6. Fill the technical sections of `REVIEW.md`; keep human-playtest items `not_tested`.
7. Set an accurate status such as `refining` (defect) or `awaiting_acceptance` (ready for human), consistent with the state machine.

<a id="wiki-lifecycle--implement--scope-change-new-approval"></a>
### Scope change = new approval

A newly needed input package, extra script, third-party asset, credential, command, release endpoint or significantly changed gameplay behavior **invalidates** the old Gate I. Stop and present:
- what changed and why;
- exact new paths/commands/dependencies and risks;
- revised `PLAN.md` `rN+1`;
- rollback/protective handling of partial work;
- explicit new authorization question.

Old approval evidence remains in history; it must not be silently rewritten to cover the new scope. Minor fixes **within** the exact approved envelope need not generate repeated gates.

<a id="wiki-lifecycle--implement--example-a-fourth-source-file"></a>
### Example: a fourth source file

Gate I permitted `game.js`, `index.html`, `style.css` and one test file. The agent discovers it needs `audio.js` to add collision feedback. If the agreed outcome can be met with visual feedback in the approved files, use that within scope. If not, stop, explain why `audio.js` is necessary, update the plan and ask for new Gate I. Never quietly create it because it's a “small file.”

<a id="wiki-lifecycle--implement--if-execution-tools-are-unavailable"></a>
### If execution tools are unavailable

Produce proposed edits/commands clearly marked as **not run** and ask the user to perform the verified steps or connect appropriate tooling. Do not claim to have executed a build, produced a local binary or inspected a browser when no such tool result exists.

<a id="wiki-lifecycle--implement--common-failures"></a>
### Common failures

**Tool permission as consent:** The coding agent has write access to the repository, so it thinks it may modify all files. Gate I is narrower.

**Silent dependency change:** A package manager upgrades versions while installing. Stop and reconcile any material difference.

**Self-acceptance:** Implementation records tests as passed and closes the sprint. Gate A remains human.

<a id="wiki-lifecycle--refine"></a>
## Stage 4 — Refine


Refinement applies **evidence from tests and human playtesting** to correct a bounded gameplay slice. It is not permission to expand the feature or edit source outside the approved technical plan.

<a id="wiki-lifecycle--refine--when-to-use"></a>
### When to use

Use after a build fails, an acceptance criterion is unmet, a player reports confusing feedback or the first prototype reveals an incorrect design hypothesis.

<a id="wiki-lifecycle--refine--the-diagnosis-loop"></a>
### The diagnosis loop

1. **Observation:** What exactly failed? Quote a real test or user's first-hand report; do not invent it.
2. **Reproduction:** What input, build, browser/device, sequence and expected behavior are known?
3. **Classification:** Is it a verified bug inside current scope, a hypothesis requiring investigation, or a new requirement/design choice?
4. **Permission:** Does existing Gate I still authorize the paths, commands, packages and risk necessary to fix it?
5. **Correction:** If in scope, make the smallest change and run approved checks. If out of scope, revise `PLAN.md` and request new Gate I.
6. **Preserve history:** Record `round-N` in `REVIEW.md`, old observations, correction, evidence and next human retest.
7. **Reassess:** Present updated test results and invite actual human evaluation.

A changed *design* may require returning to Gate D before another Gate I.

<a id="wiki-lifecycle--refine--three-categories-of-change"></a>
### Three categories of change

| Classification | Example | Correct action |
| --- | --- | --- |
| **In scope** | Approved movement code has an off-by-one boundary bug | Correct within valid Gate I, test, log |
| **Scope expansion** | Requires a new collision library not in the plan | Stop, revise plan and seek Gate I |
| **New design decision** | Player now wants a dash mechanic instead of only movement | Record/design choice, update acceptance checks, then new plan approval |

**Never** label an entire second game system “just polish.”

<a id="wiki-lifecycle--refine--example-unreadable-hazard"></a>
### Example: unreadable hazard

The player says: “I cannot tell that the red block is dangerous until I hit it.” The agent should record this as a human observation and investigate contrast, size, motion cues or onboarding. A revised border or shape within already approved CSS/canvas scope may be an in-scope refinement; adding sound assets, packages or a tutorial overlay beyond the plan may need new approval.

A learning checkpoint can ask whether the user expected color alone to be enough, then compare the next retest with that prediction. This is meaningful education, not an artificial quiz.

<a id="wiki-lifecycle--refine--rejection-is-not-erasure"></a>
### Rejection is not erasure

If the user rejects a playtest, keep the original verdict, failing criteria and feedback in `REVIEW.md`. Later `round-2` can contain a new, specific result. Do not backdate or overwrite `round-1` to make the history appear continuously successful.

<a id="wiki-lifecycle--refine--exit-criteria"></a>
### Exit criteria

The refined outcome is ready for human Acceptance only when it is actually runnable/inspectable, technical checks and known defects are reported accurately, and the human has concise steps aligned with the original criteria.

<a id="wiki-lifecycle--refine--common-failures"></a>
### Common failures

**AI reacts to criticism by redesigning the entire game:** Ask which experience needs to change; keep out-of-scope ideas in backlog.

**Partial approval forgotten:** The human authorized code but not new audio assets. Keep that boundary.

**Fake retest:** “It should work now” is prediction, not evidence. Run actual checks or label unverified.

<a id="wiki-lifecycle--acceptance"></a>
## Stage 5 — Human Acceptance


Acceptance evaluates **the actual player experience**. An agent can prepare tests, evidence and play instructions; only the human can supply the final verdict.

<a id="wiki-lifecycle--acceptance--when-to-use"></a>
### When to use

Use after an implementation or refinement cycle has an inspectable/runnable outcome, or when deciding whether a research spike answered its question.

<a id="wiki-lifecycle--acceptance--prepare-a-fair-review"></a>
### Prepare a fair review

`REVIEW.md` should contain:
- the original `AC-##` criteria from `SPRINT.md`;
- commands actually run, test outcomes and device/environment where known;
- a runnable build or an honest blocker;
- short human test steps and expected observations;
- known defects, assumptions, accessibility/device limits and release blockers;
- empty Gate A verdict fields until the human responds.

An agent may pass its unit tests but fail to create a usable build. Don't pretend the human could play the game if there is no actual artifact.

<a id="wiki-lifecycle--acceptance--playtest-the-experience"></a>
### Playtest the experience

For a movement-and-obstacle sprint, ask the person to:
1. launch the game with the verified instructions;
2. move in each direction and test boundary collisions;
3. avoid and intentionally hit obstacles;
4. restart and observe response;
5. describe whether control feel and hazard readability matched expectations.

The person's answer can be concise: “Input feels instant, but I can't see the hazard against the background.” That is more informative than a fabricated “all good.”

<a id="wiki-lifecycle--acceptance--record-gate-a"></a>
### Record Gate A

Allowed verdicts:
- **accepted** — criteria meet the human's expectations;
- **accepted_with_conditions** — accepted subject to explicitly preserved conditions;
- **needs_refinement** — correct and retest;
- **rejected** — preserve reason and decide whether to revise or abandon;
- **paused** — insufficient evidence or external blocker.

Record the actual response and source in `REVIEW.md`. Conditional acceptance **with unresolved release-blocking conditions** is not unconditional completed/releasable status.

The framework's documented Stage 6 validator may recognize internally consistent entries, but it **cannot authenticate human consent or gameplay experience**. A human verdict is not replaceable by code.

<a id="wiki-lifecycle--acceptance--closing-the-sprint"></a>
### Closing the sprint

After genuine acceptance, update `STATE.md` and `planning/BACKLOG.md` to show what is done, what remains deferred, what was learned and the next possible slice. Preserve prior refinement rounds and past human feedback.

Do **not** auto-create Sprint 002 simply because Sprint 001 closed. The person chooses the next direction.

<a id="wiki-lifecycle--acceptance--research-only-acceptance"></a>
### Research-only acceptance

A formal research-spike sprint may have criteria such as “the test produced reproducible measurements” and “we can choose between two approaches.” Human Gate A evaluates whether those *evidence deliverables* answer the agreed question—not whether an imaginary game was playable.

<a id="wiki-lifecycle--acceptance--common-failures"></a>
### Common failures

**Test success equals approval:** CI is green but user hasn't tried it. Keep `awaiting_acceptance`.

**No evidence per criterion:** A broad “done” lacks test coverage. Map each original AC to pass/fail/partial/not-tested.

**Silencing negative feedback:** An earlier rejection is removed after fixes. Preserve round history.

<a id="wiki-sprints--overview"></a>
## The Three-File Sprint Pack


A sprint is a **bounded experiment or playable increment** with a testable end. Light consolidates original ADDF's numerous sprint artifacts into `SPRINT.md`, `PLAN.md`, and `REVIEW.md` without deleting their responsibilities.

<a id="wiki-sprints--overview--when-to-use"></a>
### When to use

Read when creating Sprint 001, teaching a student how to plan gameplay, or evaluating whether a sprint can be safely continued after an interruption.

<a id="wiki-sprints--overview--the-minimum-pack"></a>
### The minimum pack

```text
planning/sprints/sprint-001/
├── SPRINT.md    # what, why, tradeoffs, AC-##, Gate D
├── PLAN.md      # how exactly, commands, dependencies, Gate I, execution
└── REVIEW.md    # actual results, human playtest, refinement, Gate A
```

The **blank project** does not contain a sprint folder. The agent copies the three distribution templates only after the human selects a milestone; it updates IDs/revisions to match `STATE.md` and `GAME.md`.

<a id="wiki-sprints--overview--responsibilities-don-t-merge"></a>
### Responsibilities don't merge

`SPRINT.md` owns **experience intent**. It records why the sprint matters, evidence, design alternatives, learning checkpoint, in/out scope, selected direction, and `AC-##` criteria. Gate D belongs here and in significant `D-###` decisions.

`PLAN.md` owns **execution scope**. It enumerates exact create/modify/move/delete paths, commands and working directories, dependencies/assets with provenance, side effects, rollback and verification. Gate I belongs here. The agent's actual command results also live here.

`REVIEW.md` owns **evidence and verdicts**. Every acceptance criterion has a real result or `not_tested`. Human observations and each refinement round remain visible. Gate A belongs here, never in a model's unverified confidence.

<a id="wiki-sprints--overview--a-good-first-sprint"></a>
### A good first sprint

A tiny dodge game could test:
- AC-01: four-direction control with arena bounds;
- AC-02: one repeating hazard clearly triggers failure;
- AC-03: restart resets the attempt.

It would exclude high-score services, audio, art-generation pipelines, multiplayer and future levels until needed. This makes a playable and inspectable outcome likely within one iteration.

<a id="wiki-sprints--overview--the-sprint-lifecycle"></a>
### The sprint lifecycle

1. Choose one backlog candidate or focused question.
2. Research and design its player outcome; draft `SPRINT.md`.
3. Obtain Gate D for meaningful choices.
4. Draft the exact `PLAN.md` dry run; obtain Gate I.
5. Implement and test inside authorized scope, recording actual evidence.
6. Refine if tests or players expose defects, re-authorizing new scope.
7. Provide a runnable artifact and ask for human Gate A.
8. Preserve the verdict, retrospective and handoff; choose the next sprint later.

A formal no-code research-spike sprint still documents its bounded plan and evidence even though it authorizes **no game code**.

<a id="wiki-sprints--overview--common-failures"></a>
### Common failures

**Premature sprint folder:** The framework creates ten empty sprints at initialization. Keep only the active selected sprint.

**Approval conflation:** Design choice is treated as permission for commands. Split D and I.

**Missing history:** A correction erases an earlier negative playtest. Preserve review rounds.

<a id="wiki-sprints--backlog"></a>
## Backlog: Keep Ideas Without Building Them Yet


The backlog collects possible player outcomes, research experiments and deferred work. Its purpose is to **protect focus** while preserving future ideas.

<a id="wiki-sprints--backlog--when-to-use"></a>
### When to use

Use when a brainstorming session produces too many ideas, when playtesting suggests a new feature, or when a designer asks why a requested system isn't in the active sprint.

<a id="wiki-sprints--backlog--one-item-observable-outcome"></a>
### One item = observable outcome

Each candidate uses a stable `B-###` ID and records title, player-facing outcome, priority, status, dependency, linked sprint (if any) and rationale.

For example:

```md
### B-003 — Clear hazard feedback
- id: B-003
- title: Clear hazard feedback
- outcome: A first-time player can identify hazards before colliding.
- priority: next
- status: candidate
- depends_on: B-001
- sprint: none
- reason: Playtest feedback suggests the first obstacle is hard to perceive.
```

Do not interpret the example as a real entry until the human actually requests or confirms it.

<a id="wiki-sprints--backlog--selecting-a-first-slice"></a>
### Selecting a first slice

A meaningful `priority: now` candidate should be small enough to answer one question. If “Build enemy AI” contains movement, animation, targeting, health and coordination, split it into separate outcomes. The user chooses consequential priorities; the agent may recommend ordering based on evidence and dependencies.

Only after selection should an item become `status: selected` and link to a real `sprint-NNN`. Backlog inclusion does not authorize implementation.

<a id="wiki-sprints--backlog--research-spikes-versus-features"></a>
### Research spikes versus features

A research spike might ask: “Can this browser build reliably access the needed controller inputs?” Its deliverable is sourced evidence or a deliberately authorized experiment, **not** a full input system. Label its outcome explicitly to avoid presenting research progress as shipped gameplay.

<a id="wiki-sprints--backlog--updates-after-playtesting"></a>
### Updates after playtesting

After the human's Gate A verdict, the agent can mark the completed slice, defer new suggestions, preserve discarded ideas with reasons, and recommend the next candidate. “Needs refinement” may stay inside the current sprint if the fix is within scope or requires a revised authorization.

Stable IDs aren't recycled when an idea is rejected. Status values include `candidate`, `selected`, `in-progress`, `completed`, `deferred` and `discarded`.

<a id="wiki-sprints--backlog--example-prioritization"></a>
### Example prioritization

A designer wants enemy waves, new art and more levels. The last test showed movement controls are inconsistent. The agent recommends fixing controls **before** enemy waves because later difficulty feedback will be unreliable otherwise. The user can disagree; the choice and reasoning should be recorded if material.

<a id="wiki-sprints--backlog--common-failures"></a>
### Common failures

**Backlog as permission:** The agent implements a “next” idea without a sprint and Gate I. Stop.

**Infinite backlog grooming:** The team spends more time ranking ideas than testing them. Prioritize only enough to select the next slice.

**Deletion without reasoning:** Rejected ideas disappear. Preserve status and reason.

<a id="wiki-sprints--planning"></a>
## Planning and the Exact Dry Run


`PLAN.md` is the boundary between thoughtful design and implementation permission. Its function is not to produce a long essay; it's to make the **real edits and effects visible to the human before they occur**.

<a id="wiki-sprints--planning--when-to-use"></a>
### When to use

Use after a bounded sprint and its acceptance checks are selected, before any game-source, test, asset, manifest or deployment configuration is edited.

<a id="wiki-sprints--planning--first-check-the-inputs"></a>
### First check the inputs

Verify the active sprint ID, `SPRINT.md` revision, selected design and Gate D evidence. Check the actual repository and known files **read-only** within `SECURITY.md` boundaries. A missing dependency or unknown engine installation should be reported, not guessed.

<a id="wiki-sprints--planning--fill-the-plan"></a>
### Fill the plan

The required dry run covers:

| Section | Practical question |
| --- | --- |
| Inputs/assumptions | Which approved sprint revision and project state are we planning for? |
| Exact file operations | What exact files are created, modified, moved or deleted, and why? |
| Commands/side effects | What commands run, where, and what do they write/download? |
| Dependencies/assets | Which versions, licenses, downloads and outside services are involved? |
| Implementation sequence | What's the smallest safe sequence? |
| Verification plan | How will each `AC-##` be tested, and who tests player feel? |
| Risks/rollback | What might break, what should stop work and how is it reversed? |
| Open ambiguities | Which unresolved questions prevent authorization? |
| Gate I | What exact revision/scope did the human approve? |
| Execution record | What actually happened after authorization? |

<a id="wiki-sprints--planning--example-dry-run-scope"></a>
### Example dry-run scope

```md
| Operation | Exact path | Purpose | Scope constraint |
| --- | --- | --- | --- |
| create | game.js | AC-01 movement | No networking or inventory |
| create | index.html | Playable arena | One page, no external embeds |
| create | tests/game.test.cjs | AC-01/02 logic | Existing Node test runner only |
```

The command section might authorize `node --test tests/game.test.cjs` in the game folder and **no package installation**. Any necessary additional command must appear in a revised plan.

A broad wildcard such as “all files needed” is not a suitable authorized scope.

<a id="wiki-sprints--planning--ask-for-a-precise-gate-i"></a>
### Ask for a precise Gate I

After showing the plan, ask: “Do you authorize Sprint 001 `PLAN.md` r1 for these paths and commands, with these exclusions?” Record the **actual reply** and its source. A user may approve only a subset; revise the plan to accurately reflect that rather than stretching the words.

Plan revision `r2` that adds a dependency or a file **requires fresh Gate I**. Preserve earlier revision/approval history; never overwrite it to imply retroactive consent.

<a id="wiki-sprints--planning--approvals-and-technical-capability"></a>
### Approvals and technical capability

An agent tool with shell access can technically run a command even before permission exists. That doesn't make it authorized. A validator that sees `gate_i_status: authorized` may check matching fields but cannot verify the human actually typed the response.

Public deployment, purchases, secret access, destructive operations or external messages require **separate explicit special approval**, not just ordinary coding Gate I.

<a id="wiki-sprints--planning--common-failures"></a>
### Common failures

**Plan without acceptance checks:** How can a reviewer judge whether files are necessary? Define `AC-##` first.

**Version mismatch:** Gate I says r1, current plan says r2. Stop and re-approve.

**Execution before authorization:** An agent runs npm install “just to inspect.” Treat the install as a side effect needing review.

<a id="wiki-sprints--approvals"></a>
## Human Approval Gates: D, I and A


Light's three gates intentionally distribute authority across **experience**, **execution**, and **evaluation**. Skipping one cannot be compensated for by extra technical tests.

<a id="wiki-sprints--approvals--when-to-use"></a>
### When to use

Use when the user asks “Can the agent just continue?”, when scope changes, or when an AI marks work complete without first-hand verification.

<a id="wiki-sprints--approvals--gate-d-significant-design-choices"></a>
### Gate D — Significant design choices

Gate D settles consequential player experience, scope, architecture or technology direction. The agent offers genuine alternatives, tradeoffs, evidence and a recommendation, then asks one direct question. Record actual choice in `DECISIONS.md` and the sprint's `SPRINT.md`.

No material design fork? A justified `not_required` may be acceptable. A trivial variable name inside existing approved behavior need not trigger a full design vote.

**Gate D never authorizes code edits.**

<a id="wiki-sprints--approvals--gate-i-exact-implementation-authorization"></a>
### Gate I — Exact implementation authorization

The agent presents `PLAN.md` before code changes. The reviewer sees:
- current revision and linked sprint;
- exact create/modify/move/delete paths;
- shell commands, directories, side effects and external service access;
- dependency versions, downloads/asset provenance;
- security, destructive or paid actions;
- test strategy, risks, rollback and exclusions.

Only clear permission for this **exact** scope allows Develop to act. Ambiguous “go ahead” about a concept is insufficient if the file/command plan wasn't shown.

**Gate I becomes stale** when files, commands, dependency/version, material behavior, risk or external effects change. The agent stops, documents the difference and requests a new gate for the revised plan.

<a id="wiki-sprints--approvals--gate-a-human-acceptance"></a>
### Gate A — Human acceptance

The agent presents the runnable artifact, actual tests, failing/untested checks and short playtest steps. The human evaluates and provides a verdict: `accepted`, `accepted_with_conditions`, `needs_refinement`, `rejected`, or `paused`.

Automated tests can establish logical behavior but cannot decide whether the mechanic feels responsive, a level is readable or an onboarding interaction makes sense.

A condition that blocks release must remain a blocker even if the human conditionally approves the sprint.

<a id="wiki-sprints--approvals--approval-records"></a>
### Approval records

Each gate has a source/revision reference and recorded human wording or durable review link. Agents may transcribe actual approvals, **never invent them**. A model's memory or generated checkbox does not independently prove consent.

Gate location:
- D: `SPRINT.md`, cross-linked to `D-###`;
- I: `PLAN.md`, reflected in `STATE.md`;
- A: `REVIEW.md`, reflected in `STATE.md`.

<a id="wiki-sprints--approvals--a-common-ambiguity"></a>
### A common ambiguity

The human says, “Yes, I like the dodge game.” This may settle a concept preference, not authorization to create files or install Phaser. The agent should acknowledge the selected direction, show the technical plan, and ask: “Do you authorize r1's exact operations?”

After implementation, “The tests all pass” isn't an acceptance verdict. Ask the human to try the game and describe whether the agreed experience works.

<a id="wiki-sprints--approvals--stop-conditions"></a>
### Stop conditions

When an approval can't be verified, degrade to a **safe non-implementation state**. Do not forge the missing record or proceed because a previous agent claimed it was approved.

<a id="wiki-sprints--approvals--common-failures"></a>
### Common failures

**Gate bundling by inference:** Treat enthusiasm as all three gates. Split the records.

**Retroactive consent:** Add new paths to r1 after its approval. Create r2 and ask again.

**AI self-acceptance:** The agent fills “human verdict: accepted.” Keep pending until real review.

<a id="wiki-sprints--review"></a>
## Review, Refinement History and Retrospective


`REVIEW.md` is the **honest record of what happened**. It links the promised `AC-##` criteria to actual automated evidence, human playtest observations and the final Gate A verdict.

<a id="wiki-sprints--review--when-to-use"></a>
### When to use

Use during technical verification, after a human tries a build, when defects lead to another round and at sprint closure or handoff.

<a id="wiki-sprints--review--one-result-per-criterion"></a>
### One result per criterion

For each actual `AC-##` in `SPRINT.md`, record:
- `result: pass | fail | partial | not_tested`;
- method: automated, manual-playtest or manual-inspection;
- who performed it (agent, human, CI, or unknown);
- actual environment/device where known;
- real source of evidence and concise notes.

Don't fill `performed_by: human` unless the human actually reports their observation. A screenshot generated by automation isn't a substitute for their experience.

<a id="wiki-sprints--review--a-useful-playtest-instruction"></a>
### A useful playtest instruction

“Launch the verified build, use arrows to move the duck toward each arena edge, then let a hazard collide. Does movement stop at the border? Can you identify hazards before impact? Does restart give control back?”

This is specific, short and tied to the original criteria. Avoid asking the user to complete a huge survey merely to exercise Gate A.

<a id="wiki-sprints--review--refinement-rounds"></a>
### Refinement rounds

Use `round-1`, `round-2` and so on to preserve:
1. trigger and observed failure;
2. diagnosis and uncertainty;
3. corrected or revised plan, and whether a new Gate I was needed;
4. actual source/test changes;
5. subsequent human retest and verdict.

**Do not overwrite old negative feedback.** A later successful round means the sprint improved; it does not mean earlier testing never failed.

<a id="wiki-sprints--review--accepted-with-conditions"></a>
### Accepted with conditions

Conditional acceptance must list specific conditions, affected criteria and any unresolved release blockers. The sprint is not unconditionally releasable while blocking conditions remain. Follow the normalized status/approval rules in the Sprint File Contract rather than assuming all “accepted” labels mean the same thing.

<a id="wiki-sprints--review--retrospective"></a>
### Retrospective

A short retrospective captures:
- intended versus observed outcome;
- design hypothesis that the experiment supported or disproved;
- technical or player-experience lessons;
- deferred work and newly discovered risks;
- next **proposed** sprint, not an automatically authorized one.

The learning outcome should be **observed or marked unverified**, not a claim that the user understood a concept simply because the agent explained it.

<a id="wiki-sprints--review--example-a-hard-to-see-hazard"></a>
### Example: a hard-to-see hazard

In `round-1`, the human reports low contrast and Gate A says `needs_refinement`. The agent corrects a visual cue inside approved scope, reruns tests and records `round-2`. The human retests. Only the **actual** new verdict can close the sprint.

<a id="wiki-sprints--review--common-failures"></a>
### Common failures

**Review after the fact:** No acceptance criteria were defined before source changes. Improve planning next sprint.

**Paper acceptance:** Tests pass and the agent fills human verdict. Keep pending.

**Lost handoff:** The next agent cannot tell which round is active. Update `STATE.md` and the review record.

<a id="wiki-learning--guided-discovery"></a>
## Guided Discovery: Ask Less, Decide Better


The point of guided discovery is not to make an AI more chatty. It's to help a designer transform uncertainty into **small, informed, human-owned choices** while maintaining a usable project record.

<a id="wiki-learning--guided-discovery--when-to-use"></a>
### When to use

Use for new game ideas, an uncertain mechanic, a student who is learning design, or a returning developer unsure how to approach the next playable feature.

<a id="wiki-learning--guided-discovery--one-meaningful-question-at-a-time"></a>
### One meaningful question at a time

The default pace is a **single consequential question** per turn. A batch of up to three related questions can be useful if the person opts for faster intake, but avoid demanding ten independent preferences before showing anything useful.

Ask a question *because an immediate decision depends on it*. “Would you prefer direct or inertia-based movement?” is actionable. “What is your favorite color and music genre?” is probably not actionable while movement hasn't been tested.

<a id="wiki-learning--guided-discovery--the-discovery-ladder"></a>
### The discovery ladder

1. **Player verb:** move, aim, rotate, trade, negotiate, connect, select, build, hide?
2. **System response:** how does the world visibly react to that verb?
3. **Player feedback:** can a novice tell what changed and why?
4. **Smallest experiment:** which five-minute playable slice will test the hypothesis?
5. **Important fork:** which difference might materially change the player's experience?
6. **Human choice:** select, defer, reject or request more evidence.
7. **Durable record:** agent updates `GAME.md`, `DECISIONS.md`, backlog and the active sprint.

Don't march through all seven as a form. Use only what the user's current answer and goal require.

<a id="wiki-learning--guided-discovery--option-design"></a>
### Option design

When proposing concepts, ensure choices differ **mechanically**. Avoid three identical dodge games wearing different themes. For each option, include one action, one response, one smallest prototype and one uncertain tradeoff.

Recommend an option when helpful, but label it clearly as a recommendation. “I don't know” should lead to a **reversible experiment or focused research**, not forced agreement.

<a id="wiki-learning--guided-discovery--example-level-design-learning"></a>
### Example — level design learning

A student wants to teach a player a new jump ability. The agent offers:
- a low-risk introductory gap with safe recovery;
- a timed obstacle requiring the jump immediately.

It explains onboarding, failure cost and feedback tradeoffs, and asks which one the student wants to prototype first. Later the playtest should reveal whether a player notices the jump cue. That's an observable learning checkpoint.

<a id="wiki-learning--guided-discovery--recording-without-bureaucracy"></a>
### Recording without bureaucracy

A selected significant choice becomes a `D-###` entry with context, options and actual human response. A minor parameter inside an already approved technical plan may remain a routine T0 detail. The agent shouldn't force the user to hand-write either record.

<a id="wiki-learning--guided-discovery--common-failures"></a>
### Common failures

**AI decides everything:** The agent presents a complete game design and asks for one approval. Break it into material choices.

**Indecision loop:** The assistant asks unlimited open questions. Offer a bounded experiment.

**Learning by lecture:** The agent explains theory without tying it to a gameplay test. Create a prediction and observation instead.

<a id="wiki-learning--checkpoints"></a>
## Learning Checkpoints Through Playable Evidence


ADDF Light Games includes learning because the human should understand the *design and engineering consequences* of the decisions the AI helps implement.

<a id="wiki-learning--checkpoints--when-to-use"></a>
### When to use

Use when teaching game mechanics, systems or level design, onboarding a nonprogrammer, or deciding which experiment to build next. A checkpoint is especially valuable when two alternatives have different player-facing tradeoffs.

<a id="wiki-learning--checkpoints--the-six-part-pattern"></a>
### The six-part pattern

1. **Concept:** One relevant principle in accessible language.
2. **Concrete example:** How this principle appears in this game.
3. **Tradeoff:** Two legitimate approaches, not a false choice.
4. **Prediction:** What the designer expects to notice during play.
5. **Test:** A real playable or observable experiment with relevant acceptance criteria.
6. **Reflection:** Actual observations, uncertainty and any new decision.

No quiz score or compulsory “correct answer” is necessary. If the user wants only the implementation summary, keep the explanation short and provide a deeper link.

<a id="wiki-learning--checkpoints--mechanic-design-example"></a>
### Mechanic design example

**Concept:** Control feel depends on acceleration and stopping behavior.

**Options:** Direct speed gives predictable response; easing/acceleration can feel weightier but needs tuning and can mask collision mistakes.

**Prediction:** “Direct controls will make hazards easier to dodge but may feel abrupt.”

**Test:** Use one obstacle type and inspect input response in a minimal arena. Record both automated movement results and the human's feeling of responsiveness.

**Reflection:** The user may find direct speed too twitchy. That observation supports a revised experiment—not a claim the AI was wrong or that a theory was “failed” definitively.

<a id="wiki-learning--checkpoints--system-design-example"></a>
### System design example

**Concept:** An enemy's state machine makes behavior legible through explicit transitions.

**Options:** Patrol/chase/return states versus a continuously evaluating goal-selection system.

**Test:** Observe whether players can tell when the enemy notices them. The first experiment might use only patrol and chase, with visual cues and one trigger.

**Reflection:** A player who cannot perceive the transition reveals a feedback-design issue; raw AI sophistication is not the only success metric.

<a id="wiki-learning--checkpoints--level-design-example"></a>
### Level design example

**Concept:** Teach an ability with a safe introductory encounter before combining it with pressure.

**Options:** Forgiving first jump versus immediate challenge.

**Test:** New player attempts the first gap with no verbal coaching; observer notes hesitation, errors, retry behavior and cue readability.

**Reflection:** The human designer decides whether the level teaches the intended mechanic.

<a id="wiki-learning--checkpoints--where-evidence-lives"></a>
### Where evidence lives

The checkpoint and prediction belong in `SPRINT.md`; actual automated/manual results and human reflection belong in `REVIEW.md`. A material change in intended player experience goes into `DECISIONS.md`.

The AI may explain a result but must not claim the person learned something without an observation supporting it.

<a id="wiki-learning--checkpoints--common-failures"></a>
### Common failures

**Performative learning:** Add an unrelated quiz to every sprint. Replace it with a relevant prediction.

**No test:** The agent explains an algorithm but no player behavior is observed. Connect theory to a slice.

**One answer is treated as universal:** One playtest supports a local design choice, not an absolute claim about all players or engines.

<a id="wiki-learning--decisions"></a>
## Decisions: Keep Human Agency and Durable Reasoning


A decision record makes it possible for another model—or the same developer next month—to understand **what was chosen, why, what was rejected and when to reconsider it**.

<a id="wiki-learning--decisions--when-to-use"></a>
### When to use

Use when the person chooses a significant mechanic, platform, architecture, scope constraint or high-impact behavior, or when a new playtest reverses a previously approved choice.

<a id="wiki-learning--decisions--decision-tiers"></a>
### Decision tiers

| Tier | Example | Authority |
| --- | --- | --- |
| **T0 routine** | Formatting, local variable naming, harmless implementation detail inside approved scope | Agent may choose |
| **T1 material** | Core mechanic, control feel, platform, feedback style, difficulty progression | Human Gate D |
| **T2 high-impact** | Paid services, public exposure, privacy/credential handling, destructive migration | Human Gate D plus stronger Gate I and separate permissions where needed |

Tier depends on **consequence**, not the number of code lines.

<a id="wiki-learning--decisions--the-record-format"></a>
### The record format

Use stable `D-001`, `D-002`, etc. Include:
- the specific question and why it mattered;
- genuine options and tradeoffs;
- sources or experiment evidence, labeled when unverified;
- AI recommendation, explicitly separate from the human choice;
- actual human response and rationale where given;
- effects on scope, criteria and implementation;
- superseded decision, if any;
- an observable revisit trigger.

If a user says “not sure,” mark it deferred, not chosen. Don't fabricate a decision just to fill the starter template.

<a id="wiki-learning--decisions--decision-example"></a>
### Decision example

**D-004 — Immediate or accelerating movement?** The user selected immediate movement because Sprint 001 is intended to isolate obstacle readability. Acceleration remains a candidate for a later feel-tuning experiment. The agent links D-004 from the active `SPRINT.md` and updates `GAME.md` without treating the choice as Gate I.

A later playtest might show oversensitive controls. Create **D-005** referencing D-004 as superseded rather than replacing the original rationale.

<a id="wiki-learning--decisions--choice-and-execution-are-distinct"></a>
### Choice and execution are distinct

A user can approve a design without approving the proposed source operations. Conversely, approval of a narrow code plan cannot be stretched to change the player experience materially. Maintain Gate D and Gate I in different files with their own references.

For an existing project, don't “migrate” earlier approvals into new scope without checking the original evidence and current worktree.

<a id="wiki-learning--decisions--avoid-excessive-logging"></a>
### Avoid excessive logging

Log material choices, not every trivial constant or naming decision. A file with hundreds of T0 entries is hard to use and makes important choices less visible.

<a id="wiki-learning--decisions--common-failures"></a>
### Common failures

**AI recommendation becomes a decision:** The agent writes `human_choice: choose A` before any real answer. Keep pending.

**Silent reversal:** New direction is documented but old decision is deleted. Preserve supersession.

**Source-less confidence:** An inference is cited as fact. Label it honestly.

<a id="wiki-agents--operating-contract"></a>
## The Agent Operating Contract


`AGENTS.md` is the standing instruction file for **the individual game project**. It defines how an assistant should read context, write project records, protect permissions and hand off work. Tool access alone never overrides it.

<a id="wiki-agents--operating-contract--when-to-use"></a>
### When to use

Read before allowing any agent to work in a game repository, when a provider adapter conflicts with local instructions, or when an agent has lost context.

<a id="wiki-agents--operating-contract--session-startup"></a>
### Session startup

An agent should:
1. read `SECURITY.md` **before** arbitrary file discovery;
2. read `AGENTS.md` and `STATE.md`;
3. load only relevant `GAME.md`, `DECISIONS.md`, backlog and active sprint files;
4. verify actual worktree/branch and last known gate evidence where tools permit;
5. state the current **verified** status, uncertainties and one safe next action.

A prior model's summary is a clue, not permission to resume an unapproved command.

<a id="wiki-agents--operating-contract--research-design-develop-capabilities"></a>
### Research, Design, Develop capabilities

Research gathers evidence and may prepare research notes in allowed documentation. It does not change game code, scenes, tests or assets.

Design drafts game intent, decision options, `SPRINT.md`, `PLAN.md` and relevant project memory. It does not change implementation files.

Develop is the only capability that may modify game implementation, and **only** within a human-approved Gate I revision/scope. This applies even when the user-facing stage is “Refine.”

One model may move between capabilities, but it must respect their boundaries.

<a id="wiki-agents--operating-contract--one-model-versus-many-agent-setup"></a>
### One-model versus many-agent setup

A solo coding agent can perform all planning and authorized implementation with the same files. A coordinator plus specialist workers can divide research, design, coding and verification, but **delegation does not convey approval**. A worker must verify Gate I itself before writing.

Provider-specific skills are thin adapters. They should not become separate competing sources of project authority.

<a id="wiki-agents--operating-contract--required-output-behavior"></a>
### Required output behavior

An agent should distinguish:
- what it actually observed or executed;
- what it inferred or proposes;
- which files it changed and which approval allows them;
- which tests ran and which remain unverified;
- what requires the next human decision.

It should not claim a GitHub commit, playable build or passing test absent tool evidence.

<a id="wiki-agents--operating-contract--example"></a>
### Example

A Codex agent is told, “Continue the duck game.” It opens `STATE.md` and finds `awaiting_approval`, `PLAN.md` r2, but the only human consent points to r1. Correct behavior: report the stale plan and ask for renewed Gate I, **not** start implementing r2 because the user's broad message said continue.

<a id="wiki-agents--operating-contract--common-failures"></a>
### Common failures

**Provider priority confusion:** A tool's instruction suggests broad edits that conflict with project security. Stop and reconcile.

**Chat as memory:** The agent never updates `STATE.md`. Record durable facts before handoff.

**Self-assigned authority:** A coordinator claims it approved a worker. Only actual human Gate D/I/A applies.

<a id="wiki-agents--permissions"></a>
## Agent Permissions and Special Operations


ADDF Light Games separates **technical capability** from **human authorization**. An installed agent may have filesystem or terminal access, but that does not automatically permit source edits, installing packages or publishing a game.

<a id="wiki-agents--permissions--when-to-use"></a>
### When to use

Use when assigning tools to a coding agent, when a plan includes a package install or risky command, or when handling a request involving remote machines and connected services.

<a id="wiki-agents--permissions--default-permissions"></a>
### Default permissions

| Capability | May do | Must not do |
| --- | --- | --- |
| Research | Inspect allowed sources, gather facts, propose options | Modify game code or decide material user intent |
| Design | Draft the project brain and sprint plan, record actual human choices | Edit game scenes/assets/tests or run unapproved implementation commands |
| Develop | Make exact approved file operations and run approved commands | Expand scope or self-authorize |
| Coordinator | Route permitted tasks and summarize evidence | Grant Gate D/I/A, assume worker result or background permission |

**Planning Markdown** may be drafted within the user's requested task, subject to `SECURITY.md`. Changes to safety policy that weaken restrictions need explicit human review.

<a id="wiki-agents--permissions--what-gate-i-must-specify"></a>
### What Gate I must specify

The plan lists exact paths and operations, shell commands with working directories, expected files, dependency versions/sources, network effects, risks, rollback and tests. A broad “make any necessary changes” scope is invalid.

A **material change** to those elements requires a new plan revision and renewed Gate I.

<a id="wiki-agents--permissions--separate-high-impact-permissions"></a>
### Separate high-impact permissions

Require specially explicit approval for:
- deleting substantial data, reset/rebase that might erase unrelated work;
- reading secrets or transferring private code/data externally;
- installing an unknown dependency or downloaded script;
- publishing a game, deployment, branch merge or access-control change;
- purchases, paid APIs, third-party messages, unattended jobs and remote shell tasks.

Even an ordinary authorized `PLAN.md` does not imply these special effects unless they were specifically reviewed.

<a id="wiki-agents--permissions--existing-project-protections"></a>
### Existing-project protections

For existing repositories, inventory instructions and worktree state **read-only** before migration. An install command may change lockfiles or engine project settings. A “helpful cleanup” may delete another person's work. Don't perform either without a reviewed scope and recovery plan.

<a id="wiki-agents--permissions--permission-check-example"></a>
### Permission check example

A student permits edits to `PlayerController.cs` and the movement test, with a Unity build command. The coding agent discovers it needs a new package or wants to modify the input-actions asset. Those paths and dependencies weren't authorized. It stops, discloses the actual reason, updates the plan and asks again.

Routine variable naming inside an approved C# file does **not** require a separate human decision unless it changes the intended behavior or risk.

<a id="wiki-agents--permissions--if-the-agent-cannot-verify-approval"></a>
### If the agent cannot verify approval

Return to `awaiting_approval` or `paused`, preserving safe work. Do not fabricate a source reference, replay a destructive command, or infer that yesterday's model had valid permission.

<a id="wiki-agents--permissions--common-failures"></a>
### Common failures

**Sandbox = authorization:** It isn't; host permissions are a ceiling, not consent.

**Special effects hidden in build step:** `npm install` or cloud deployment can have network/data side effects. Show them.

**Unattended autonomy by default:** A scheduler or coordinator exists, so the agent keeps working. Require explicit user-controlled schedule/scope first.

<a id="wiki-agents--handoff"></a>
## File-First Handoffs and Safe Resumption


The core ADDF promise is that the **project remains understandable after the chat disappears**. Another model should be able to orient itself from durable project files, test evidence and current source state.

<a id="wiki-agents--handoff--when-to-use"></a>
### When to use

Use after a long pause, switching from browser chat to a home coding agent, swapping Claude/Codex, delegating work, or recovering from a crashed terminal session.

<a id="wiki-agents--handoff--the-required-resumption-order"></a>
### The required resumption order

1. Load `SECURITY.md` first.
2. Load `AGENTS.md` and `STATE.md`.
3. Load `GAME.md`, `DECISIONS.md`, and current backlog as relevant.
4. If `active_sprint` exists, read its `SPRINT.md`, `PLAN.md`, and `REVIEW.md`.
5. Verify current branch/worktree and actual changed files where tools permit.
6. Compare Gate D, Gate I and Gate A records with **real human evidence** and relevant plan/review revisions.
7. Report the last verified stage/status, work completed, tests actually run, blockers and one safe next action.

A remembered “we were approved yesterday” is insufficient when the current `PLAN.md` has changed.

<a id="wiki-agents--handoff--handoff-packet-when-coordinating-multiple-agents"></a>
### Handoff packet when coordinating multiple agents

A temporary handoff should contain:
- project/sprint identifier and last verified stage/status;
- requested role (research/design/develop/verify);
- exact safe read files and exclusions;
- permitted writes and commands, or explicit **none**;
- plan revision and real Gate I evidence (or no permission);
- expected verifiable output and stop conditions.

An optional coordinator may format this packet, but cannot approve source changes on the human's behalf. A coding worker should independently verify the same source records.

<a id="wiki-agents--handoff--handle-uncertain-command-outcomes"></a>
### Handle uncertain command outcomes

If a remote agent timed out after a build/install/write, **do not blindly retry** a potentially non-idempotent command. Check whether its effects already occurred. Record evidence or label outcome unknown.

The same applies to a Git push, deploy or asset export: the agent's final chat message may be missing even though a tool action succeeded.

<a id="wiki-agents--handoff--resumption-example"></a>
### Resumption example

A user opens Codex after designing on a phone. `STATE.md` says `awaiting_approval` for Sprint 002; `PLAN.md` r3 lists two C# scripts and one test. The user never approved r3. Correct Codex behavior: summarize the plan and request Gate I. It can discuss the intended mechanic but cannot silently write the scripts.

If the user later approves r3, the coder can implement only that scope and append truthful evidence for the next review.

<a id="wiki-agents--handoff--update-the-project-at-session-end"></a>
### Update the project at session end

Record any real decisions, new blockers, actual changed paths/tests, last valid approval reference and one next action. Do not inject a fictional timestamp if no clock is available. Keep secrets out of state and handoff messages.

<a id="wiki-agents--handoff--common-failures"></a>
### Common failures

**Conversation-only continuity:** All decisions disappear when a model context resets. Write them to files.

**Assumed completion:** Worker says “done,” but actual diff/tests aren't inspected. Verify before reporting success.

**Old gate reused:** Plan changed after approval. Degrade to unapproved and ask again.

OpenClaw is an **optional coordinator** for scheduling or routing AI tasks in a trusted workspace. ADDF Light Games does **not** require OpenClaw, and installing a skill does not provision a remote development machine, messaging channel or unattended task.

<a id="wiki-agents--openclaw--when-to-use"></a>
### When to use

Use when multiple agents or devices need coordinated research, planning, coding and review. Avoid introducing a coordinator for a small single-agent game prototype unless it genuinely reduces friction.

<a id="wiki-agents--openclaw--what-a-coordinator-may-do"></a>
### What a coordinator may do

A properly configured coordinator can read permitted project-brain files, ask human design questions, delegate safe research, prepare scope proposals and aggregate **actual** worker evidence. It must not treat its own assignment as a human approval.

The project's `SECURITY.md`, `AGENTS.md`, current `PLAN.md` and actual human gate responses remain authoritative.

<a id="wiki-agents--openclaw--installation-boundary"></a>
### Installation boundary

The Stage 4 adapter includes `integrations/openclaw/skills/addf-light-games/SKILL.md`. It is intended to be copied deliberately to an OpenClaw workspace skill path, for example:

```text
<workspace>/skills/addf-light-games/SKILL.md
```

Workspace location and tool availability vary. Confirm the installed version, exact paths, permissions and credential isolation. Do not automatically enable remote shell, continuous background tasks, cron, public deployment or messaging channels.

<a id="wiki-agents--openclaw--safe-delegation-packet"></a>
### Safe delegation packet

Before asking a coding worker to act, specify:
- game project and active `sprint-NNN`;
- verified stage/status;
- exact safe read files;
- exact permitted write paths/operations;
- approved commands, directories, dependency list and risk boundaries;
- current Gate I revision **and real human source reference**;
- expected output/test evidence;

<a id="wiki-quality--testing"></a>
## Testing: Prove Behavior, Not Permission


Technical tests are essential evidence for a game sprint, but they're not proof of player understanding, a valid human approval, or the quality of the entire game.

<a id="wiki-quality--testing--when-to-use"></a>
### When to use

Use while planning acceptance criteria, implementing authorized game behavior, triaging failed builds or preparing a sprint for human acceptance.

<a id="wiki-quality--testing--separate-kinds-of-evidence"></a>
### Separate kinds of evidence

| Test type | Examples | What it can establish |
| --- | --- | --- |
| Unit | Collision geometry, inventory rule, movement bounds | Logic behaves as expected for covered inputs |
| Integration | Input event reaches player state; scene loads dependencies | Connected systems interact under tested conditions |
| Browser/engine smoke | Game starts, input works, pause/restart, no runtime errors | Runnable behavior in a known environment |
| Visual inspection | Obstacle visible, HUD text legible | Observed rendering, sometimes environment-specific |
| Human playtest | Control feel, clarity, difficulty and onboarding | A real person's experience, with limitations |
| Framework contract validation | Required Markdown files, approvals and state references | Recorded structural consistency only |

A passing unit test doesn't tell us whether a player recognizes a dangerous object; a screenshot doesn't tell us whether the game responds reliably to controls.

<a id="wiki-quality--testing--write-criteria-before-implementation"></a>
### Write criteria before implementation

`SPRINT.md` should define actual `AC-##` entries with method, setup, action, observable pass condition, evidence location and whether the criterion blocks release. The plan maps technical tests to these criteria and lists **approved commands**.

`REVIEW.md` then records what was actually run. Use `not_tested` for missing evidence, not a guessed `pass`.

<a id="wiki-quality--testing--scope-and-commands"></a>
### Scope and commands

A coding agent may only run verification commands allowed by the current Gate I. A command that downloads dependencies or changes lockfiles has side effects; it belongs in the exact plan. If the environment lacks the engine or required test runner, report that blocker and ask the user how to proceed.

A CI workflow on the framework branch validates framework material. It does **not** automatically authorize or execute tests in a separate user's private game repo.

<a id="wiki-quality--testing--stage-5-worked-pilot"></a>
### Stage 5 worked pilot

The browser Duck Dodge example includes pure JavaScript game logic tests, a Chromium interaction smoke test and a synthetic approval-policy test model. The executable checks cover movement, hazard collision and certain stop rules.

Those tests do **not** prove the user's individual browser can open the file, that the obstacle is readable or that live Claude/Codex/OpenClaw obey every gate. The example records these gaps rather than marking them green.

<a id="wiki-quality--testing--negative-case-tests-matter"></a>
### Negative-case tests matter

Test what the framework **rejects**, not just what it accepts: missing `SECURITY.md`, stale plan revision, unbounded file operation, missing human Gate A, missing `AC-##` results and conflicting status.

For game code, test boundary conditions, failure paths, pauses, restarts and invalid input—not only an ideal playthrough.

<a id="wiki-quality--testing--common-failures"></a>
### Common failures

**Build is green, sprint is done:** Request human Gate A.

**Predicted test result becomes evidence:** Actually execute the test or mark not verified.

**Silent side effect:** A test helper downloads packages without approval. Review commands and dependencies first.

<a id="wiki-quality--playtesting"></a>
## Human Playtesting and Design Validation


Game development cannot be evaluated entirely from code structure or generated screenshots. A person must interact with the game and report what actually happens and how it feels.

<a id="wiki-quality--playtesting--when-to-use"></a>
### When to use

Use after an authorized playable slice, when a designer needs to validate a mechanic/system/level, and before assigning a final Gate A verdict.

<a id="wiki-quality--playtesting--design-the-playtest-around-a-question"></a>
### Design the playtest around a question

A good playtest asks “Does the first-time player understand that the red square is dangerous?” rather than “Is the game fun?” The latter is too broad for an early slice and difficult to diagnose.

Choose a narrow objective:
- **Mechanic:** Is the movement or jump response predictable?
- **System:** Can players infer how an enemy chooses its target?
- **Level:** Does the first encounter teach the required action?
- **Feedback:** Can players see and understand a collision or success event?
- **Accessibility:** Can relevant players perceive and operate the test in the intended environment?

<a id="wiki-quality--playtesting--prepare-a-short-protocol"></a>
### Prepare a short protocol

1. Specify the exact build, device and controls.
2. Tie tasks to the original `AC-##` criteria.
3. Let the player attempt the task before explaining it away.
4. Record actual observations, surprises, frustration and helpful recovery behavior.
5. Distinguish the player's actions from the designer's interpretation.
6. Capture the human's Gate A verdict separately from automated evidence.

In a classroom, another student can be a playtester, but the project owner still decides what to accept. Preserve which person actually observed which result.

<a id="wiki-quality--playtesting--example-testing-a-level-s-first-jump"></a>
### Example: testing a level's first jump

The designer predicts the player will notice a safe jump cue and cross a short gap without verbal instructions. During the test, the observer notes hesitation, camera angle, failed attempts and whether the player retries. The feedback may suggest changing geometry or introducing a clearer visual cue.

If the change needs a new asset/path outside the approved plan, return to Gate I rather than treating feedback as blanket permission.

<a id="wiki-quality--playtesting--what-to-record"></a>
### What to record

`REVIEW.md` can use a simple table:

| Criterion | Human action | Actual observation | Outcome |
| --- | --- | --- | --- |
| AC-01 | Attempts jump | Character responds, lands on platform | Pass for observed player/device |
| AC-02 | Reads hazard cue | Player walks into hazard without noticing | Fail/needs refinement |
| AC-03 | Retries | Player finds restart prompt | Pass |

One individual's report is **local evidence**, not proof all players will respond the same way. Record device, experience level and accessibility constraints if relevant and known.

<a id="wiki-quality--playtesting--feedback-to-refinement"></a>
### Feedback to refinement

State the concrete defect, propose a minimal correction and decide whether it fits current authorization. Retest only after a real build and capture the new round without erasing prior feedback.

The human may accept, accept with conditions, request refinement, reject or pause.

<a id="wiki-quality--playtesting--common-failures"></a>
### Common failures

**Designer coaches every action:** A novice never reveals what instructions are unclear. Observe first.

**Tests become a survey only:** Aesthetic opinions replace observable tasks. Mix questions with real actions.

**AI invents observations:** A model estimates how a player would feel. Mark it a hypothesis, never a playtest result.

<a id="wiki-quality--validation"></a>
## Automated Contract Validation


Stage 6 introduced a **read-only Python validator** for the six core project-brain files and, when active, the three sprint files. It is intended to catch obvious missing, inconsistent or overbroad records—not to certify a safe agent or authenticated consent.

<a id="wiki-quality--validation--when-to-use"></a>
### When to use

Run after installing the starter kit, changing core project records, resuming a sprint with uncertain state, before implementation, or in CI for framework templates.

<a id="wiki-quality--validation--run-from-the-framework-clone"></a>
### Run from the framework clone

For a blank distributed kit:

```bash
python3 scripts/validate_light.py starter-kit/minimal --mode template --sprint-template starter-kit/sprint-template
```

For your separate game repository:

```bash
python3 /path/to/ADDF/scripts/validate_light.py /path/to/my-game
```

Machine-readable output: add `--format json`. To make warnings exit nonzero in automation: add `--strict`.

No pip packages are required; Python 3.10+ and the local files suffice. The validator does not read arbitrary game source, run game tests, install dependencies or access secrets intentionally.

<a id="wiki-quality--validation--what-errors-look-like"></a>
### What errors look like

The validator reports rule IDs:
- `L-F001`: missing required file;
- `L-F002`: missing/duplicate required heading/key;
- `L-F003`: invalid project/sprint ID;
- `L-F004`: invalid enum or state;
- `L-F005`: duplicate decision/backlog/criteria IDs;
- `L-F006`: broken relative Markdown links;
- `L-F007`: unsafe/broad authorized operation;
- `L-F008`: acceptance-criterion coverage missing;
- `L-F009`: active Gate I/revision mismatch;
- `L-F010`: incomplete recorded human gate;
- `L-F011`: cross-file consistency issue.

Warnings `L-H001` and `L-H002` explicitly say that alleged human consent and historic authorized scope cannot be independently authenticated from text.

<a id="wiki-quality--validation--interpret-results-honestly"></a>
### Interpret results honestly

**PASS** means the checked file structure and recorded state are internally consistent. It is **not** proof the current user approved, a game works, or all optional integrations are safe.

**WARN** means structure passed but an important limit remains; use judgment and real evidence before coding.

**FAIL** means the project record needs correction. Do not “fix” a failed Gate I by inventing approval text.

<a id="wiki-quality--validation--ci-and-regression-tests"></a>
### CI and regression tests

The Light-only `.github/workflows/validate-light-games.yml` checks the starter templates, Stage 6 Python tests and Stage 5 Node tests. It runs on the `ADDF_light_games` branch, not original ADDF `main`. It does **not** deploy GitHub Pages or publish games.

Stage 7 adds **documentation/manual drift checks** separately; they do not expand the game project's write authority.

<a id="wiki-quality--validation--example-failure"></a>
### Example failure

If `STATE.md` says `implementing` but `PLAN.md` still shows `gate_i_status: pending`, the validator fails. The agent should inspect real approval evidence and return to a safe state, **not** mark the plan authorized to make the test pass.

<a id="wiki-quality--validation--common-failures"></a>
### Common failures

**Validator as security tool:** Assume Python checks prove consent or absence of secrets. They don't.

**Optional docs made mandatory:** Reject a novice project for not having release architecture files. Only the minimal contracts are required.

**Self-repair of human records:** A model fills in fabricated responses to silence warnings. Keep the warning and ask the person.

<a id="wiki-quality--failure-recovery"></a>
## Failure Recovery: Stop, Preserve, Reconcile


Failures are expected in development. The goal is not to avoid every problem; it is to **keep the project safe and make the next action explicit**, without rewriting evidence or expanding permissions.

<a id="wiki-quality--failure-recovery--when-to-use"></a>
### When to use

Use when a test fails, a plan is stale, a coding agent edited an unexpected path, a remote command times out, or a user rejects a playable prototype.

<a id="wiki-quality--failure-recovery--classify-the-failure"></a>
### Classify the failure

| Failure | Immediate safe response |
| --- | --- |
| Test/build failure inside approved scope | Record actual output, diagnose, correct only within valid Gate I |
| New file/dependency needed | Stop, revise `PLAN.md`, obtain renewed Gate I |
| Unauthorized file change | Stop, disclose exact diff, preserve work, ask user about rollback or plan revision |
| Missing or ambiguous approval | Fail closed, set safe state, ask for evidence or renewed consent |
| Secret/credential exposure | Stop reads/transfers, avoid repeating secret, discuss containment with human |
| Remote timeout | Treat outcome unknown; inspect actual state before retrying |
| Human playtest rejection | Preserve `REVIEW.md` verdict, propose refinement/re-design, seek needed gates |
| Conflicting project files | Report conflict, establish safest authority, reconcile with human |

<a id="wiki-quality--failure-recovery--the-recovery-sequence"></a>
### The recovery sequence

1. **Stop** the risky action; don't repeatedly retry.
2. **Record verified facts**: current file diff, command and known result, status, affected paths, possible external effects.
3. **Separate assumptions**: what may have happened but wasn't confirmed?
4. **Check authorization**: does the current plan still cover the proposed correction?
5. **Propose bounded remedy**: smallest safe fix, exact files/commands, rollback and tests.
6. **Request necessary human gate**: Gate D if intended behavior changes; new Gate I if technical scope changes; Gate A after retest.
7. **Update durable state**: blockers, next actor, and actual evidence in `STATE.md`, `PLAN.md` and `REVIEW.md`.

Don't force-reset Git or delete uncommitted work without an explicitly reviewed recovery operation.

<a id="wiki-quality--failure-recovery--example-failed-build-after-package-install"></a>
### Example: failed build after package install

An authorized plan expected package version 1.x, but the installer pulled 2.x and changed a lockfile not in scope. The agent should stop, report actual version/lockfile changes and risks, then ask whether to revert within safe authorized recovery or approve a revised plan. It should not silently continue and claim the original version was used.

<a id="wiki-quality--failure-recovery--example-remote-workflow-interruption"></a>
### Example: remote workflow interruption

A home-machine agent starts an authorized export, then a school-browser session loses connection. The coordinator cannot assume the export failed. Reopen the actual target workspace and verify artifacts, timestamps, command logs and final state before rerunning. Never publish an unverified artifact.

<a id="wiki-quality--failure-recovery--retrospective-as-learning"></a>
### Retrospective as learning

A useful review explains why the failure happened and what control could prevent recurrence: clearer scope, smaller slice, tighter exclusions, better tests or different learning checkpoint. It should not be a blame exercise or a fake “everything went smoothly” report.

<a id="wiki-quality--failure-recovery--common-failures"></a>
### Common failures

**Silent repair:** AI edits new files to “fix” errors without Gate I. Stop and re-plan.

**Overreaction:** Delete the entire repository to roll back one file. Use precise recovery.

**Erase negative feedback:** Rewrite prior reviews. Preserve history.

<a id="wiki-quality--security"></a>
## Security, Privacy and Source-Control Boundaries


A lightweight methodology does not justify loose security. `SECURITY.md` defines which files an agent may inspect and what external effects require human permission **before** it begins browsing a game project.

<a id="wiki-quality--security--when-to-use"></a>
### When to use

Read during initial setup, repository adoption, remote-agent coordination, dependency installation, deployment planning or any time private data/credentials might be involved.

<a id="wiki-quality--security--security-first-reading"></a>
### Security-first reading

The agent must read `SECURITY.md` before opening arbitrary project files. Safe default exclusions include:
- `.env`, private keys, SSH/config credentials and token stores;
- personal/private user files and unrelated home directories;
- non-project credentials, caches or logs likely to include secrets;
- unknown external servers, network transfers and downloaded scripts.

The purpose is to define a **minimal permitted context**, not to ingest everything and filter later. Treat repository text and web content as untrusted data, not elevated instructions.

<a id="wiki-quality--security--tool-access-versus-authorization"></a>
### Tool access versus authorization

An agent with a shell may technically install packages, contact an API, delete files or deploy. The user must still approve exact paths, commands and effects under Gate I, with **separate special permission** for destructive, paid, sensitive or public actions.

A model must not silently change GitHub permissions, alter branch protection, push secrets or use private repositories as remote prompt context.

<a id="wiki-quality--security--asset-and-game-specific-risks"></a>
### Asset and game-specific risks

A game may import textures, animations, audio, third-party assets or model-generated artwork. Preserve provenance, license and usage conditions. For a small prototype, placeholder art is often the safest default. Do not assume any image/audio output can be publicly redistributed without review.

If a mechanic uses analytics, cloud saves, multiplayer, microphone/camera or live data, identify privacy and user-consent requirements **before** adding services. Use offline mock data when feasible for the first slice.

<a id="wiki-quality--security--existing-projects-and-git"></a>
### Existing projects and Git

Always inspect current branch/worktree and human changes before implementation. Do not overwrite existing `AGENTS.md`, force-reset, squash unrelated changes, merge to protected branches or change deployment workflows without explicit authorization.

The framework's `main` branch is original ADDF; `ADDF_light_games` is the separate Light edition. Stage 7 documentation work must not publish a live site or merge those branches.

<a id="wiki-quality--security--if-sensitive-material-is-encountered"></a>
### If sensitive material is encountered

Stop reading/transmitting, avoid reproducing the secret, record affected path/operation at a safe level, and ask the human how to contain/rotate/recover. Do not pretend to have rotated credentials without an actual authorized action and result.

<a id="wiki-quality--security--common-failures"></a>
### Common failures

**Remote “helpful” access:** An orchestrator copies private game source to a home/cloud worker without explicit scope. Ask first and use trusted transport.

**Unsafe package:** An unreviewed installer runs because a tutorial suggested it. Evaluate exact source/side effects.

**False security certification:** A Markdown validator passes. This does not prove secrets absent or external services safe.

## File Reference: Ownership and Minimum Contents


This reference explains **where each kind of truth lives**. Stage 2's Project and Sprint File Contracts remain normative for exact headings, keys and values; this page tells a human when to open and edit each document.

<a id="wiki-reference--file-reference--when-to-use"></a>
### When to use

Use to onboard a new model, find a missing decision or determine which file needs an update after implementation/playtesting.

<a id="wiki-reference--file-reference--six-persistent-game-project-files"></a>
### Six persistent game-project files

| Path | Canonical responsibility | Who decides? | When updated? |
| --- | --- | --- | --- |
| `SECURITY.md` | Excluded context, secret boundaries, tool/external-effect limits | Human/security policy; agent can propose tightening | Setup, new risk, tool changes |
| `AGENTS.md` | Session behavior, stage/capability boundaries and approval gates | Human adopts permissions | Setup or reviewed policy change |
| `GAME.md` | Player experience, mechanics, pillars, constraints, first playable hypothesis | Human confirms meaningful intent | Discovery or material design change |
| `STATE.md` | Current verified stage/status, active sprint, approval summary, next action | Agent derives from actual evidence; human controls gates | Any transition, blocker, handoff |
| `DECISIONS.md` | Significant `D-###` choices and reversals | Human owns T1/T2 choice | Decision made, deferred or superseded |
| `planning/BACKLOG.md` | Candidate `B-###` outcomes and research spikes | Human sets material priority | Ideas discovered, scope deferred, sprint closed |

A **blank** project has these six files and no sprint directory. `unknown` values are honest and valid. The agent fills records as the user answers; the user should not have to hand-author the files.

<a id="wiki-reference--file-reference--three-files-in-an-active-sprint"></a>
### Three files in an active sprint

| File | Main sections | Gate |
| --- | --- | --- |
| `planning/sprints/sprint-NNN/SPRINT.md` | Reason, player outcome, in/out scope, research, alternatives, learning, criteria, risks | D |
| `planning/sprints/sprint-NNN/PLAN.md` | Exact file operations, commands, dependencies/assets, implementation sequence, verification, rollback, execution record | I |
| `planning/sprints/sprint-NNN/REVIEW.md` | Build/test evidence, `AC-##` results, playtest steps, human observations, refinement rounds, retrospective | A |

For a specific game the three files must agree on `sprint_id`, `project_id` and `sprint_kind`. `PLAN.md` revisions use `r1`, `r2`, etc.; Gate I only applies to the current approved revision/scope.

<a id="wiki-reference--file-reference--what-is-not-mandatory"></a>
### What is not mandatory

Architecture diagrams, deeper research reports, asset provenance logs, feature packages, releases, extra command registries and risk matrices are **optional modules**, not required at initialization. Add them when they solve a real coordination problem.

The original full ADDF's `DOMAIN.md`, `COMMANDS.md`, `QUESTIONS.md`, `RISKS.md`, separate dry runs and detailed sprint records may contain critical history. Do not erase them during an existing-project migration.

<a id="wiki-reference--file-reference--documentation-versus-project-truth"></a>
### Documentation versus project truth

The distribution repository contains `spec/`, `docs/light-games/`, `prompts/`, `starter-kit/`, `integrations/` and `examples/`. Its generated `MANUAL.md` is a *reference artifact*, not a game project's living state.

When wiki prose conflicts with exact contract fields, consult the approved `spec/` schema and current human decision before changing template behavior. A future framework update must be intentionally migrated into existing game projects.

<a id="wiki-reference--file-reference--common-failures"></a>
### Common failures

**Everything in STATE:** One file stores all decisions and test results. Use it as summary; preserve source in decisions, plan and review.

**Approval in comments only:** A chat says “authorized” but plan revision isn't recorded. Keep unapproved.

**Premature advanced docs:** A beginner receives 20 blank files. Stay minimal until necessary.

<a id="wiki-reference--prompt-catalog"></a>
## Prompt Catalog: What to Ask the Agent Next


The nine **agent-neutral lifecycle prompts** live under the framework distribution's `prompts/` directory. They're useful as copyable instructions in ordinary chat and as a common contract behind optional provider skills.

<a id="wiki-reference--prompt-catalog--when-to-use"></a>
### When to use

Use when choosing the next command for a new or resumed project, switching models, or diagnosing why a coding agent skipped an approval checkpoint.

<a id="wiki-reference--prompt-catalog--prompt-lookup"></a>
### Prompt lookup

| Prompt | Use it when | Safe stop point |
| --- | --- | --- |
| **START** | First encounter or unknown stage | Entry route, verified context, one question |
| **DISCOVER** | No idea, broad idea, unsure player verb | Small concepts and actual user direction |
| **RESEARCH** | Technical/design uncertainty could change next slice | Sourced findings and meaningful decision |
| **DESIGN** | Ready to define a testable outcome | Sprint and actual Gate D |
| **PLAN** | Want exact technical operations | Dry-run `PLAN.md`, stop for Gate I |
| **IMPLEMENT** | Current plan revision genuinely authorized | Actual edits/test results within scope |
| **REFINE** | Playtest/test reveals an issue | In-scope fix or revised Gate I |
| **ACCEPT** | A runnable/inspectable deliverable exists | Human Gate A and retrospective |
| **RESUME** | New session or model context loss | Verified state and one safe next step |

The [canonical prompt catalog](https://github.com/Walabrolu4/Autonomous-Duck-Development-Framework/blob/ADDF_light_games/prompts/LIGHT_GAMES.md) links to all nine full text files. The original `prompts/README.md` and mode folders still belong to the inherited full ADDF edition.

<a id="wiki-reference--prompt-catalog--how-to-select-one-prompt"></a>
### How to select one prompt

Do **not** automatically chain START→DISCOVER→RESEARCH→DESIGN→PLAN→IMPLEMENT→ACCEPT in a single autonomous run. Choose the prompt that matches the **verified** status in `STATE.md` and stop at the next meaningful gate.

For example, `awaiting_approval` means show `PLAN.md` and request Gate I; it does not mean “IMPLEMENT as soon as the agent sees a plan file.”

<a id="wiki-reference--prompt-catalog--example-handoff-from-browser-to-coding-agent"></a>
### Example — handoff from browser to coding agent

In a browser chat, the human selected one mechanic and the agent drafted `SPRINT.md`. Later they open Codex on the project repo. The first Codex action is RESUME: read the files, verify status/approval, then PLAN if technical scope remains unfinished. Gate D from the browser conversation **does not** substitute for Gate I in the coding environment.

If no file tools exist, the assistant supplies proposed Markdown and explicit limitations rather than claiming it changed the repository.

<a id="wiki-reference--prompt-catalog--provider-adapters"></a>
### Provider adapters

- Claude Code: optional skill in `.claude/skills/addf-light-games/SKILL.md`.
- Codex: optional skill in `.agents/skills/addf-light-games/SKILL.md`.
- OpenClaw: optional workspace skill and coordinator playbook.

Each adapter is a host-friendly wrapper, not an independent approval authority or proof of live integration testing. Check that your installed host actually discovers and follows the skill before relying on it.

<a id="wiki-reference--prompt-catalog--common-failures"></a>
### Common failures

**Prompt as magic automation:** A pasted IMPLEMENT prompt authorizes unplanned writes. The actual human Gate I still matters.

**Wrong branch/version:** Use original full-ADDF prompts while intending Light. Check the edition and project instructions.

**No evidence after execution:** A model tells a story about tests. Require actual command output or mark not verified.

<a id="wiki-reference--troubleshooting"></a>
## Troubleshooting ADDF Light Games


Use symptoms and **actual evidence** to recover. Don't repair an approval failure by writing a fake approval, or an implementation failure by expanding scope without human review.

<a id="wiki-reference--troubleshooting--when-to-use"></a>
### When to use

Use when onboarding feels stuck, a skill isn't discovered, the validator fails, a sprint can't close, or another agent resumes with contradictory state.

<a id="wiki-reference--troubleshooting--common-problems"></a>
### Common problems

<a id="wiki-reference--troubleshooting--i-don-t-know-what-to-make"></a>
#### “I don't know what to make”

Start at DISCOVER and ask for two or three **mechanically different** small ideas. The user can select one or ask for a reversible experiment; no full GDD is necessary.

<a id="wiki-reference--troubleshooting--the-agent-keeps-asking-too-many-questions"></a>
#### “The agent keeps asking too many questions”

Limit to one consequential question per turn by default. Let the agent choose T0 routine details within approved scope. Put irrelevant future preferences into the backlog, not the current session.

<a id="wiki-reference--troubleshooting--a-blank-starter-kit-fails-validation"></a>
#### “A blank starter kit fails validation”

Check whether the exact six Light `minimal/` files were copied, not the original full `starter-kit/blank/`. An unstarted project should have `active_sprint: none`, `discovering`, `authorized: no`, and no sprint folder. Run the validator in `--mode template` if checking the distribution starter templates themselves.

<a id="wiki-reference--troubleshooting--missing-security-md-required-heading"></a>
#### “Missing SECURITY.md / required heading”

The validator reports `L-F001` or `L-F002`. Inspect the file; don't overwrite an existing human-owned file to silence the check. Create a missing new-project file or propose a reviewed migration.

<a id="wiki-reference--troubleshooting--the-agent-says-it-has-permission-but-validation-fails"></a>
#### “The agent says it has permission but validation fails”

Inspect `STATE.md`, the exact `PLAN.md` revision, Gate I human response and source, and current worktree. If any mismatch or unverified source exists, **stop and request renewed consent** rather than fabricating text.

<a id="wiki-reference--troubleshooting--the-human-chose-the-mechanic-so-why-hasn-t-it-coded"></a>
#### “The human chose the mechanic, so why hasn't it coded?”

Gate D selected a design. The coding agent must still show exact file paths, commands, dependencies, risks and rollback, then obtain Gate I on that scope.

<a id="wiki-reference--troubleshooting--a-new-dependency-is-needed-mid-sprint"></a>
#### “A new dependency is needed mid-sprint”

Stop implementation, revise `PLAN.md` to rN+1, disclose new install/network/license effects and request fresh Gate I. Don't silently extend r1.

<a id="wiki-reference--troubleshooting--the-build-passed-but-the-sprint-won-t-close"></a>
#### “The build passed but the sprint won't close”

Check whether the human has actually run the game and given a Gate A verdict. Automated test success does not equal human acceptance. Ensure each `AC-##` has a result and known release blockers are visible.

<a id="wiki-reference--troubleshooting--the-game-opens-but-feels-wrong"></a>
#### “The game opens but feels wrong”

Record a concrete observation, classify it against original criteria, and propose one minimal correction. Use existing Gate I only if scope remains valid; otherwise re-plan.

<a id="wiki-reference--troubleshooting--the-new-claude-codex-skill-isn-t-loading"></a>
#### “The new Claude/Codex skill isn't loading”

Verify the exact installed skill path, frontmatter and host version. Ensure you installed into the **game project**, not merely left files in the framework repo. Do not weaken permissions or overwrite existing instructions. Stage 5 host-specific tests remain a separate task.

<a id="wiki-reference--troubleshooting--openclaw-didn-t-reach-my-home-pc"></a>
#### “OpenClaw didn't reach my home PC”

An adapter skill is **not a remote transport**. Configure trusted workspace and connection only after a separate user-approved setup. Don't claim background work or machine access unless actually available.

<a id="wiki-reference--troubleshooting--a-resumed-model-wants-to-repeat-a-command"></a>
#### “A resumed model wants to repeat a command”

First verify whether the command already ran and what side effects occurred. If outcome is uncertain, avoid blind retries—especially package installs, deletes, deploys or Git operations.

<a id="wiki-reference--troubleshooting--the-documentation-and-manual-md-disagree"></a>
#### “The documentation and MANUAL.md disagree”

The wiki under `docs/light-games/` is canonical. The manual is generated. Run `python3 scripts/build_light_manual.py --check` to detect drift, regenerate only in a reviewed Stage 7 documentation change, and never manually edit the generated manual.

<a id="wiki-reference--troubleshooting--escalation"></a>
### Escalation

If the problem is a **material design choice**, return to the human Gate D. If it is **technical scope/permission**, return to Gate I. If it's **player experience**, ask for human Gate A or refinement. If it's **security, data loss or privacy**, stop affected work and seek explicit recovery authorization.

<a id="wiki-reference--faq"></a>
## Frequently Asked Questions


<a id="wiki-reference--faq--do-i-need-an-ai-coding-agent-to-start"></a>
### Do I need an AI coding agent to start?

No. Plain chat and Markdown are enough for ideation, research, planning and producing proposed file edits. A coding agent becomes useful **after Gate I**, when a particular set of implementation operations has been authorized.

<a id="wiki-reference--faq--do-i-need-to-know-programming"></a>
### Do I need to know programming?

Not to begin. Light can support learning through relevant tradeoffs and small experiments. A person still needs to evaluate the game's actual behavior and make material design choices.

<a id="wiki-reference--faq--can-i-start-without-an-idea"></a>
### Can I start without an idea?

Yes. The agent should offer two or three mechanically distinct options and ask one meaningful question at a time. “I don't know yet” is a valid response.

<a id="wiki-reference--faq--does-light-mean-weaker-safety-than-original-addf"></a>
### Does Light mean weaker safety than original ADDF?

No. It reduces daily file/navigation burden but preserves role boundaries, a dry run, exact implementation authorization, file-backed memory and human acceptance. See the [comparison table](#wiki-foundations--comparison).

<a id="wiki-reference--faq--is-addf-light-games-a-game-engine"></a>
### Is ADDF Light Games a game engine?

No. It can guide a web Canvas/Phaser game, Godot or Unity project, or another playable system. It doesn't automatically install any of them.

<a id="wiki-reference--faq--why-six-project-files-and-three-sprint-files"></a>
### Why six project files and three sprint files?

The six persistent files hold safety, rules, game intent, current status, decisions and backlog. Once a sprint exists, three files separate the **what** (`SPRINT.md`), **how/authorization** (`PLAN.md`) and **results/acceptance** (`REVIEW.md`).

<a id="wiki-reference--faq--why-not-ask-ai-to-generate-my-entire-game"></a>
### Why not ask AI to generate my entire game?

Large one-shot outputs hide assumptions and make playtesting difficult. Bounded slices expose the important mechanic early and let a human learn from actual feedback.

<a id="wiki-reference--faq--can-the-agent-make-any-decisions"></a>
### Can the agent make any decisions?

Yes, routine reversible T0 implementation details inside approved scope. It cannot choose significant mechanics, architecture, cost/privacy risks or player acceptance without human authority.

<a id="wiki-reference--faq--is-a-green-github-actions-check-proof-that-a-game-is-ready"></a>
### Is a green GitHub Actions check proof that a game is ready?

No. It can establish specific tested behavior or structural consistency. It cannot prove the player's experience or that a human actually approved the current plan.

<a id="wiki-reference--faq--can-the-validator-verify-that-i-approved-something"></a>
### Can the validator verify that I approved something?

It can check whether an approval *record* has consistent fields and a matching revision. It cannot authenticate the actual human or reconstruct the exact historical plan snapshot from Markdown alone. Treat warnings seriously.

<a id="wiki-reference--faq--can-i-use-my-existing-project"></a>
### Can I use my existing project?

Yes, through a **read-only audit and reviewed migration**. Don't overwrite existing `AGENTS.md`, source files or GDD. Preserve original ADDF history if the project already uses it.

<a id="wiki-reference--faq--what-about-claude-code-codex-and-openclaw"></a>
### What about Claude Code, Codex and OpenClaw?

All are optional integrations. Stage 4 created skill adapters; Stage 5 live host-specific runtime validation remains pending. OpenClaw's coordinator does not automatically provision remote computer access or uninterrupted background jobs.

<a id="wiki-reference--faq--must-i-use-github"></a>
### Must I use GitHub?

No. Local files are the minimum. Git is helpful for revisions, diffs and provenance, but the methodology is not tied to a specific hosting site.

<a id="wiki-reference--faq--what-if-i-reject-a-sprint"></a>
### What if I reject a sprint?

Preserve the rejection and observations in `REVIEW.md`. The agent proposes refinement or abandonment, seeking fresh Gate D/I as needed. It cannot silently mark the sprint accepted.

<a id="wiki-reference--faq--what-if-i-change-my-mind-mid-sprint"></a>
### What if I change my mind mid-sprint?

Record the new significant choice, revise affected scope/criteria and invalidate stale technical approval. The agent should explain the smallest safe way forward.

<a id="wiki-reference--faq--how-is-the-complete-manual-maintained"></a>
### How is the complete manual maintained?

The wiki pages are canonical, listed in an ordered manifest. `scripts/build_light_manual.py` generates `MANUAL.md` with stable chapter anchors and rewrites internal links. CI checks that the committed manual matches generated content.

<a id="wiki-reference--faq--common-failures"></a>
### Common failures

**Assuming the FAQ overrides exact contracts:** It doesn't. Follow the approved `spec/` files and current project evidence.

**Assuming a skill is installed because the repo contains it:** Verify actual host discovery.

<a id="wiki-reference--remote-development"></a>
## Remote Development and Access — Devices, Tools, Previews and Testing


**Framework status:** Required **reference chapter** for ADDF Light Games documentation; an **optional workflow** for individual game projects. **No new mandatory game-project file, service, subscription, credential or always-on agent is introduced.**

An iPad, tablet, borrowed computer, school lab or low-powered laptop can act as an interface while a trusted host performs coding, builds and tests. The goal is to **preserve project continuity and actual human playtesting** without confusing a remotely accessible tool with permission for an agent to run it.

<a id="wiki-reference--remote-development--when-to-use"></a>
### When to use

Use this guide when:
- you want to vibe-code in T3 Code while inspecting the same code in VS Code;
- you need to work from an iPad with your game and coding tools on a Windows, macOS or Linux host;
- you need an interactive browser-game preview or a streamed Unity/Unreal Editor;
- you are choosing between an always-on home workstation and an on-demand cloud environment;
- you are preparing an agent handoff, remote build or human Gate A playtest across devices.

**Not required** for a student working entirely on one computer. The framework must still operate locally with ordinary Markdown files and any supported assistant.

<a id="wiki-reference--remote-development--1-understand-the-three-locations"></a>
### 1. Understand the three locations

| Location | What runs there | Typical examples |
| --- | --- | --- |
| **Client** | The interface you touch; may show a code editor, agent chat or running preview | iPad Safari, another laptop, school browser |
| **Development host** | Real Git checkout, files, Codex/Gemini agent processes, terminal, installed tools and build commands | Windows 11 desktop, Mac, Linux machine, cloud workspace |
| **Preview/test target** | The actual runtime that renders the game or executes a test | iPad Safari, browser on host, Windows Unity player, remote-desktop stream |

An iPad running a browser client **does not inherently have a local Unity Editor or the project's Node/Python/engine toolchain**. The host does most execution. The preview target may be **different** from the build host: this matters when reporting test evidence.

A cloud agent is another execution environment, not automatically the same files as your home PC. Verify Git commit, active branch and uncommitted changes before assuming both environments share state.

<a id="wiki-reference--remote-development--2-tool-selection-matrix"></a>
### 2. Tool selection matrix

| Tool / workflow | What it adds | Best use | Important limits |
| --- | --- | --- | --- |
| **T3 Code remote access / T3 Connect** | Agent conversations and supported previews accessible from mobile/web while agents run on a host | AI-directed iteration using an existing coding-agent setup | Host availability, account/device approvals and installed provider support; does not itself authenticate ADDF approval |
| **VS Code Remote Tunnels + vscode.dev** | Browser code editing, Git diff, remote terminal and relevant forwarded developer services | Independent review, debugging, running *authorized* tests from iPad | Authenticated remote host must run; browser extensions and local/remote features differ |
| **T3 + VS Code together** | Agent interface plus a conventional editor on **the same working directory** | Preferred hybrid workflow for ADDF Light | A separate Git worktree or remote environment can make files appear “out of sync” |
| **Safari or other target browser** | Direct HTML5/Phaser/Canvas/Three.js/WebGL input/playtest | Human Gate A on browser games | Mobile viewport, memory, browser restrictions and touch input differ from desktop |
| **Sunshine host + Moonlight client** | Low-latency streaming of a Windows game/desktop with controller support | Unity/Unreal interactive editing, native game playtests | Remote streaming affects latency, video quality and some input behavior; not a native iPad engine |
| **Tailscale or equivalent trusted private network** | Private network path between owned devices | Reach approved local services without public router port forwarding | Configure access controls and authentication; not a substitute for app-level permissions |
| **GitHub Codespaces or supported cloud coding agent** | Cloud-hosted files and execution without needing home PC awake | Off-device coding, builds and browser previews | Distinct workspace, quotas/costs, secrets policy, graphical engine limits |

This is a *capability map*, **not** an endorsement that every item works on every platform/version, or that consumer AI subscriptions can be shared through an unauthorized proxy.

<a id="wiki-reference--remote-development--3-recommended-ipad-windows-hybrid-workflow"></a>
### 3. Recommended iPad + Windows hybrid workflow

<a id="wiki-reference--remote-development--prepare-your-host"></a>
#### Prepare your host

1. On the Windows PC, identify the **exact game repository**, active Git branch, and working tree. Keep any existing human edits intact.
2. Install/configure your preferred **first-party coding agents** on that host using their supported sign-in methods. T3 Code is optional; ADDF does not require Claude, Codex, Gemini, OpenClaw or API keys.
3. Set up T3 Code's supported remote access, if using it. In current T3 documentation, host setup is under **Settings → Sharing & access**; enable remote connection for the intended environment, authenticate, and require approval for new devices where available.
4. Enable **VS Code Remote Tunnels** on that same trusted host. Microsoft documents the command **Remote Tunnels: Turn on Remote Tunnel Access...** and the authenticated browser client at https://vscode.dev.
5. If the host is a Windows PC using WSL2, choose whether the project and tools run in **Windows or the WSL2 filesystem**; open the exact same environment/path in both interfaces.
6. Prevent unplanned sleep when you genuinely need remote access. Use an explicit security-conscious power policy rather than broadly disabling security controls.

**No remote setup occurs automatically by installing ADDF Light.** Initial login, device pairing, background services, network configuration and host permissions remain user-controlled operations.

Official references:
- T3 Code remote access: https://github.com/pingdotgg/t3code/blob/main/docs/user/remote-access.md
- VS Code Remote Tunnels: https://code.visualstudio.com/docs/remote/tunnels
- VS Code for the Web: https://code.visualstudio.com/docs/remote/vscode-web

<a id="wiki-reference--remote-development--work-from-the-ipad"></a>
#### Work from the iPad

1. Open the host-connected T3 Code client using its supported mobile app or https://app.t3.codes, if configured. Confirm the correct **environment**.
2. Open https://vscode.dev in Safari, connect through the authenticated Remote Tunnel, and select the **same project root** and branch/worktree.
3. Put the agent interface and editor side by side with iPadOS multitasking if your device supports it. A third browser window can hold the playable preview.
4. In T3 Code, ask the agent to read `SECURITY.md`, `AGENTS.md`, `STATE.md`, then the relevant sprint records. You can remain in the **same visible conversation** while progressing between workflow stages.
5. Review `SPRINT.md` and the exact `PLAN.md` revision in VS Code **before granting Gate I**. The host application's write-access permission is not equivalent to ADDF Gate I.
6. After approving the precise scope, let the agent edit the specified files, and inspect the **actual Git diff** in VS Code. Run only explicitly approved verification commands.
7. Open the game preview on the iPad, test the gameplay yourself, and supply real observations for `REVIEW.md` and Gate A.

**Critical detail: Git worktrees.** T3 Code may create an isolated working tree. Two programs showing the same repository *name* may still point to **different physical directories/branches**. Resolve the agent's exact workspace path, check `git status` and `git rev-parse --show-toplevel` where permitted, and open that path in VS Code. Do not copy or overwrite files blindly to “sync” them.

<a id="wiki-reference--remote-development--4-run-a-browser-game-and-access-its-preview"></a>
### 4. Run a browser game and access its preview

For a dependency-free HTML/JS prototype, a simple HTTP server **on the host** is usually enough. For example, after a human has authorized the relevant command in a game project's `PLAN.md`:

```powershell
# Run in the folder containing index.html (Windows host with Python installed)
python -m http.server 8000 --bind 127.0.0.1
```

The address `http://127.0.0.1:8000` refers to the **host**, not automatically to the iPad. Typing it directly into iPad Safari ordinarily points at the iPad itself and will not reach the PC.

Use **one approved connection mechanism**:
- **T3 preview / its supported remote preview tunnel**, if the installed version exposes the running port.
- **VS Code's authenticated port-forwarding/preview functionality**, verifying the URL and access level.
- **A private network path such as Tailscale**, with a deliberately scoped/accessible bind and firewall rule, or a private HTTPS service. Do **not** expose the test server publicly just to load it on a tablet.

Never bind a development server to every network interface or make its forwarded URL public without review. A local Python server is suitable for a small static game, **not** production deployment or exposure of the project's whole repository.

For Phaser/Vite/other tooling, use the *project's actual approved dev-server command* instead of assuming every project uses Python. Confirm the served root excludes credentials and private files.

Useful official references:
- Microsoft port forwarding: https://code.visualstudio.com/docs/debugtest/port-forwarding
- Tailscale private access: https://tailscale.com/docs/how-to/connect-to-devices
- Tailscale Serve (restricted private HTTPS): https://tailscale.com/docs/use-cases/application-testing/share-local-dev-server-with-team

<a id="wiki-reference--remote-development--5-automated-tests-browser-playtests-and-game-engines"></a>
### 5. Automated tests, browser playtests and game engines

| Project | Execute on host | Inspect/play from iPad | What counts as evidence |
| --- | --- | --- | --- |
| **HTML5, Canvas, Phaser, Three.js** | Approved JavaScript unit/build/test commands and dev server | Safari preview, touch/keyboard/controller as applicable | Recorded command output plus actual device/browser playtest notes |
| **Unity** | Unity editor/build pipeline on Windows/macOS (licensed and installed as needed) | Compatible WebGL build in Safari; or remote desktop/streamed editor | Engine/build log and human observations, with platform limitations |
| **Unreal** | Unreal editor/build/cook/test on Windows/macOS/Linux host | Stream actual host app/game; test native builds on their intended platform | Host verification plus separate streamed playtest, noting latency |
| **Godot or other native game** | Engine/headless checks or native game on host | Compatible web export or remote stream where supported | Distinguish browser export from native execution |
| **CLI tests / CI** | Host terminal or authorized CI runner | Read test logs and diffs | Test names, exact command, result, environment and known untested cases |

Example test command **only if it belongs to the approved game/project plan**:

```bash
node --test examples/completed-game/tests/game.test.cjs
```

A green build from the host means those tests passed **there**. It does not prove that a player could interact with the game in iPad Safari, nor that touch or controller input is correct. A human testing in Safari can supply Gate A for the **observed** experience; record if the target platform was different.

For Unity/Unreal/editor-heavy work, an iPad cannot run the full desktop editor natively. Sunshine on the host and Moonlight on the iPad can stream it as an optional path:

- Sunshine: https://app.lizardbyte.dev/Sunshine/
- Moonlight: https://moonlight-stream.org/
- Moonlight iPad app: https://apps.apple.com/us/app/moonlight-game-streaming/id1000551566

When evaluating controls, remember that remote streaming introduces network/video/input latency. Confirm important timing-sensitive mechanics again on the target hardware before claiming broad acceptance.

<a id="wiki-reference--remote-development--6-addf-authorization-remains-unchanged"></a>
### 6. ADDF authorization remains unchanged

**Remote access is an execution environment, not a workflow stage or permission level.** All existing human gates apply:

| Gate | Remote-work interpretation |
| --- | --- |
| **D — Design** | Human chooses the testable experience and significant design alternatives |
| **I — Implementation** | Human authorizes **exact game files, commands, package/install effects, ports/network exposure and other side effects** under the current `PLAN.md` revision |
| **A — Acceptance** | Human actually plays or inspects the resulting artifact and records the verdict; the agent cannot self-accept |

If remote setup itself requires new privileged services, credentials, device enrollment, unattended execution, firewall changes or a public URL, those actions need **separate, explicit user authorization**. They are not silently bundled into a harmless game-code Gate I.

A host permission dialog may ask whether an agent can write a file or execute a command. ADDF Gate I is a **separate project-specific authorization**. Both must be respected.

At handoff or provider switch, verify the latest real game state, branch/worktree and plan revision **even if the T3 UI carries over the visible conversation**. No new conversation is required merely to switch Research/Design/Develop capability.

<a id="wiki-reference--remote-development--minimal-project-specific-checklist-optional"></a>
#### Minimal project-specific checklist (optional)

You do **not** need a `REMOTE_ACCESS.md` in every game repository. When a project actually uses remote access, note relevant verified details in its existing `SECURITY.md`, `STATE.md` or an **optional local runbook**, without adding secrets:

- target host/runtime and which worktree is canonical;
- trusted connection method (not passwords, auth tokens or pairing links);
- approved server ports/commands and who may expose them;
- expected preview device/browser and accessibility controls;
- shutdown/revocation instructions and what counts as Gate A evidence;
- known limitations (iPad input, remote latency, offline host).

<a id="wiki-reference--remote-development--7-security-and-availability-checklist"></a>
### 7. Security and availability checklist

Before working remotely, verify:

1. **Authentication:** use supported identity flows, device approval and MFA where available. Keep remote access private to trusted devices.
2. **Network:** prefer authenticated tunnels or private networks. Never publish a raw agent server, remote editor, debug port, file server or game-project root on the open internet.
3. **Secrets:** store tokens in provider/OS credential stores; never in `STATE.md`, prompts, Git, log captures or remote share links.
4. **Authorization:** distinguish host/tool permissions from Gate I. Avoid blanket unattended commands or write access.
5. **Source safety:** verify Git status and active worktree before every material operation; preserve unrelated human edits.
6. **Preview isolation:** serve only the intended build output; keep development environments and test data out of public previews.
7. **Recovery:** know how to revoke device access, disable T3 Connect, turn off VS Code tunnels and stop forwarded servers.
8. **Host reality:** a PC that is sleeping, switched off, disconnected or logged out of a needed service may be unreachable.
9. **Untrusted devices:** do not persist credentials or open sensitive project files on unmanaged school or shared machines unless permitted by policy.

A VPN such as Tailscale controls connectivity; it does not replace the game's `SECURITY.md`, provider login controls, or human consent. See [Security](#wiki-quality--security) and [Agent permissions](#wiki-agents--permissions).

<a id="wiki-reference--remote-development--8-validate-a-remote-workflow-before-relying-on-it"></a>
### 8. Validate a remote workflow before relying on it

Record outcomes honestly as **passed**, **failed**, **not tested** or **user-reported**.

1. From the iPad, connect to the **intended host** in T3 and to the same project through VS Code.
2. Verify the same branch, current commit and worktree; inspect a harmless source file in both views.
3. Ask the agent to make a **documentation-only proposed change**. Confirm it is visible in VS Code without accidental duplication.
4. Present an implementation request **without Gate I**. The agent must stop without changing game code.
5. Authorize a specific, low-risk `PLAN.md` revision. Verify only the approved files change.
6. Run a listed test on the host and inspect its actual output from the iPad.
7. Open a private browser preview on the iPad and playtest at least one original acceptance criterion.
8. Record manual observations in `REVIEW.md`, preserve remaining blockers and obtain actual human Gate A.
9. If changing provider in the **same visible T3 conversation**, confirm the incoming model re-reads/reconciles source state and does not treat chat continuity as approval.
10. Disconnect and reconnect safely; confirm access can be revoked and no unexpected public service remains exposed.

An **unverified** mobile connection, remote host, preview or manual playtest is not a successful end-to-end remote-development test merely because the docs describe it.

<a id="wiki-reference--remote-development--9-troubleshooting"></a>
### 9. Troubleshooting

**T3 and VS Code show different code:** Check the exact directory, active Git worktree, branch, and uncommitted files. Do not force-sync blindly.

**The server works on Windows but not on iPad:** Host `localhost` is not the tablet's `localhost`; use an authenticated preview/forwarding mechanism or deliberately configured private network route.

**VS Code opens but the terminal is missing:** Check that the browser session is actually connected through the **Remote Tunnel**, not only browsing a remote GitHub repository. Browser-only editing lacks the same execution capabilities.

**AI keeps coding after switching models:** Stop; re-read `SECURITY.md`, `STATE.md`, `PLAN.md`, real Gate I evidence and source diff. Tool/model switching grants no implementation permission.

**A Unity/Unreal game is hard to control remotely:** Stream the actual host desktop/game or export a compatible browser build; document latency and retest on target hardware.

**Your home PC is off:** Use an explicitly approved cloud runner (e.g., Codespaces) or wait until the host is online. A browser client does not make a shut-down PC run builds.
